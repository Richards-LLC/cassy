Nightly index rebuild started timing out after 2026-07-29

Investigation / diagnostic · practitioner audience · 2026-08-07 · source: 2026-08-07-index-rebuild-timeouts.md

Verdict

The rebuild is not slower — it is doing 4.1× more work. A migration on 2026-07-29 dropped the partial index that let the incremental path skip unchanged rows, so every nightly run now performs a full scan.

Confidence: high. The behavior reproduces on demand and reverses when the index is restored.

3 Migration 121 (2026-07-29) drops idx_docs_dirty_partial while rebuilding docs, and never recreates it. migrations/m121_docs_reshape.rs:88 Names the mechanism and the date, matching #1 exactly.

5 Recreating the index on that same restore returns the run to 12m 04s. Local reproduction, snapshot snap-2026-08-06 The cause is sufficient as well as necessary.

Reasoning

Evidence 1 and 2 constrain the cause to something that changed on one day and multiplied read volume without changing write volume. Evidence 3 supplies a change on precisely that day with exactly that effect, evidence 4 confirms the mechanism in the live plan, and evidence 5 closes the loop by reversing it.

Ruled out

  • Data growth. The docs table grew 2.3% over the window; a 4.1× scan increase cannot follow from it.
  • Concurrency / noisy neighbor. CPU and IO wait were flat across the step change; the slow runs are CPU-bound in the scan.
  • Job code change. The rebuild job's last commit predates the window by five weeks (git log -1 -- jobs/rebuild).

What would falsify this

A run that stays at ~46 minutes with idx_docs_dirty_partial present and analyzed would refute the verdict outright. Likewise, finding the index still present in the production schema would move the cause to planner selection rather than a missing index — the first check on rollout is therefore \d+ docs against production, not against the snapshot.
