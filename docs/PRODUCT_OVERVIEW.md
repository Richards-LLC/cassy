## Pitch

Cassy is a local-first multi-agent coding factory and persistent context system for developers working in Git repositories.
The `cas` binary runs a supervisor with isolated workers; `cas serve` gives coding agents durable project context through MCP.
Tasks, memories, rules, skills and repository knowledge live in one local store; Cloud sync, the machine hub and the Commander browser app are optional.
Every delivery is checked before it merges: tests, the journeys a change touches, documentation upkeep and, after release, a live post-release check.

`cas doctor` also identifies guidance that still explicitly names an absent or
disabled MCP server, listing record IDs and file locations for review while
preserving the original rules, skills, memories and brief templates.

Projects declare their main journeys in the existing QA registry. Finding priority comes from severity × reach: reproduced broken main journeys precede theoretical code-read findings, which go to P4 backlog. The theoretical exception is money/data loss on a declared main journey (P2). Staffing theoretical work while a main-journey FAIL is unowned produces an advisory nudge. `factory.focus_mode` follows every worker/reviewer brief; see [triage](qa/triage.md).

Managed project updates recognize the owned content Cassy previously wrote, including uncommitted generated settings. A genuine conflict preserves only that path in the working tree and index while other settings and skills refresh. The update summary and SessionStart name the preserved files for review.


## Personas

- **Operator** - the repository maintainer: starts factory sessions, picks the work, reviews delivery evidence, approves releases and can answer from Commander.
- **Supervisor agent** - plans epics, assigns one task at a time to workers, merges pushed deliveries once CI is green and the plan target is met, and coordinates with supervisors on other projects or machines.
- **Worker agent** - executes one assigned task in its own worktree, runs the targeted tests, and pushes a committed result for review.
- **QA reviewer** - walks the journeys a delivery touches on the real build and records an approve or reject verdict in a QA ledger.

## Core Concepts

- **Provider account** - a Claude or Codex subscription identified by provider account and organization/workspace IDs, displayed by login email; `cas accounts list` shows usage, absolute resets and duplicate or login findings while legacy folder names remain launch aliases.
- **Worker task queue** - an ordered backlog for one worker. Closing or parking starts the next eligible task on its own target branch in the current conversation by default. Opt in with `factory.restart_worker_between_tasks=true` to recycle between tasks while keeping the name, worktree and launch recipe; automatic restarts default off. MCP results report measured context occupancy at the configured threshold; unavailable harness accounting is labeled unknown. Supervisors inspect, reorder or clear pending work, and stale entries carry skip notes.
- **QA candidate** - an exact-revision binary for a QA walk. A worker requests one for its own active task, and the factory daemon builds it, one at a time per machine, and messages the worker the hash and receipt. Each revision keeps its own directory, so a later build never replaces a cited one.
- **Factory session** - a live supervisor and its worker fleet, coordinated through the terminal UI. A supervisor exit prints each worker's task, dirty and unpushed work, confirmed stop and task recovery after leaving the terminal UI, and retains that evidence in the session-end receipt. Only confirmed stopped workers have unfinished task bindings released; unverified stops retain their recovery evidence. Shell hooks refuse pattern-based process signals for every factory role, including native subagents inheriting the supervisor role; agents signal the PID they started.
- **Worker spawn admission** - isolated MCP spawns choose a free factory branch name before queueing or task binding; an explicit colliding name is refused with its branch ref. Account refusals distinguish missing default homes, logged-out accounts and configuration mismatches, with the existing account-selection explanation included.
- **Build placement across machines** - saturated spawn admission can route a new task and full brief to a fresh supervisor on another machine of the same account and repository. Peers publish slots, load and pressure; selection prefers free slots then load per CPU, with one new route per peer per 90 seconds. Routes expire after 15 minutes or stale presence, and disabling `factory.auto_route_builds` releases them to local admission. Existing worker assignments stay local.
- **Bounded waits** - a merged delivery without a reusable verdict goes directly to supervisor reconciliation; it never asks the worker to repeat a close that cannot create approval. An approved pre-merge verification queues the supervisor to continue the merge with the same proof. Legacy approvals give the worker five minutes to retry close before one supervisor escalation. A dispatch whose verifier still heartbeats or is building or testing in its verifier lane has its deadline moved ten minutes out each sweep, up to one hour after the request; a verifier that stops just after an extension is reported up to about twelve minutes late. A dispatch timed out by close shares the daemon's expiry relay; unresolved waits beyond its 24-hour history window retain one deadline alert, and missing local task rows do not erase recent expiries. Native background jobs stay busy while user-work descendants use CPU; unconfirmed, quiet jobs become stalled after the configured stall window even if the harness itself ticks. Without user jobs, harness CPU can still prove inference.
- **Progress watchdog** - a factory session with open work (assigned open, in-progress, blocked or awaiting-merge tasks) and no task, lane or message change for 45 minutes wakes its supervisor once with what is waiting on whom; still nothing after another 45, it pages the operator in Commander once. Heartbeats, liveness and Cassy's own relays never count as progress.
- **Delivery relay ownership** - PR-lane failures, merged-delivery timeouts and worker merge wakes follow the worker’s local registration and factory session. Replicated tasks for another machine stay quiet; a foreign merge observation cannot record its receipt before the owning daemon delivers the wake.
- **Detached worker commands** - Capped background runs persist worker/task ownership and their exit status and log path. The worker receives one completion wake, with daemon recovery after interrupted delivery. Live runs and candidate builds suppress idle alerts; a live registered run for the worker's current task also suppresses direct stall nudges, even after its launch tool returns. Finished runs restore ordinary stall detection. Each completed run starts one idle episode whose alert names the exit, and unchanged episodes stay quiet.
- **Epic / Task** - an epic is a larger outcome built from tasks; a task is a prioritized work item with a lease, notes, an owner and close requirements.
- **Status evidence** - tool output distinguishes committed writes from completed follow-up, recorded worktree lifecycle state from current containment, and cached origin refs from live publication. Release reports count listed changes; doctor names local release-tag containment. [Status word definitions](status-words.md) map the words to their checks and name unavailable evidence.
- **Retained worker work** - supervisor startup and `cas factory gc report --full` inventory actual Git worktrees after shutdown, including checkouts outside the active store. Unpublished commits or dirty files retain worker/task identity, HEAD, counts and recovery guidance; unavailable probes are explicit. Epic status warns about later local work even when an older delivery was squash merged. These diagnostics never recover or remove work.
- **Stakeholder ask ownership** - a task's `external_ref` records its Slack thread or GitHub issue/PR source. MCP creation and staffing check existing shared claims, naming a competing supervisor, machine and task before local work changes; GitHub aliases share a claim across independent cards. A live supervisor can authorize a deliberate second GitHub task with a recorded reason. Source claims renew while local work remains and release on close/cancel. Slack keeps its supervisor-only claim/handoff authority. Unavailable advisory checks are reported for coordination.
- **Release train** - one integration per release: fixes merge to the train, the train goes through the gate once. A task created with no epic or target joins the open release-train epic, cut from the integration branch (`factory.epic_base_branch`, else the default branch), so its delivery merges locally into the train; a cut train stops accepting new tasks and refuses further merges into its lane, including after landing and closure; new tasks open or join the next train from the integration branch. Unfinished deliveries remain assigned until explicitly retargeted. A landed idle train closes on the next create. While a train is open, `worktree_merge` refuses direct main/trunk targets, including `allow_trunk`; a one-item hotfix train ships with `scripts/release.sh --hotfix` through the same release path. With no train open, direct-trunk merge behavior is unchanged; `factory.release_train=false` restores per-task targets.
- **Epic split** - two supervisors divide one epic's tasks; each side's claim is refused to the other until the split is accepted, cancelled or expires.
- **Worktree** - a separate Git checkout and branch that isolates a worker's changes; under disk pressure, build caches left by removed checkouts are reclaimed oldest first. A confirmed default-branch merge queue routes an authorized delivery through a source PR and expected-head auto-merge before touching local main. Unknown protection keeps the normal merge path; a protected-push refusal restores only that attempt's local merge, preserving operator edits and concurrent history, with source cleanup deferred until publication. A delivery PR ejected by a failed merge-queue run returns Open to its own worker once, with the failing job and tests as the change request; a second failed run of the current delivery tip leaves it parked and pages the operator, while stale runs and failures shared with the group entry ahead change nothing.
- **Delivery branch** - the pushed `factory/<name>` branch a task is proven and merged from; a supervisor `rebind_branch` approves a replacement branch after an audit of the old tip. An attributable target-sync merge advances the parked delivery and QA to that pushed tip, even when it adds no authored commits. A required ledger-only regeneration after that merge binds proof and park to the final pushed tip.
- **Required release imports** - A supervisor change-request reason pins release or sibling history with `merge_source=<full commit SHA>`, bound to the task target. Only the authenticated supervisor request handler grants these imports; quoted QA/verifier findings and queue-ejection text grant nothing.
- **Close gate** - the evidence, test-receipt and merge checks that decide whether a delivery may close; each merge records its CI admission as green, advisory or override. Default-branch deliveries reuse successful merge-group CI for an exact landed tree containing the delivery, avoiding a duplicate scoped suite. Cassy discovers the run from its recorded landing, or a close can cite `merge_group_run=<id>` without an override. Missing or mismatched queue evidence still requires scoped proof; declared-risk, content, CI and QA checks retain their evidence requirements.
- **Queue health** - Setup, doctor and release preflight share [advisory queue diagnostics](branch-protection/README.md#2-merge-queue).
- **Merge on green** - `READY TO MERGE` requires an owned, pushed delivery with green CI and worker completion: either the task is awaiting merge or the worker declared that tip ready, in a task note or a typed ready message, by its full or short SHA. A green checkpoint alone never signals completion, and an explicit merge of an in-progress task returns an unparked-task warning. Required task verification reviews an immutable merge candidate outside the target lock before publication. An already-bound task verifier can finish late on the same current source and candidate tree; a deadline does not discard that completed review, while changed or superseded candidates still refuse. When a merge queue publishes its own merge commit, close accepts the original synthetic-candidate approval only when the task's bound source is contained and its complete patch was present at the first landing; later ordinary edits retain that approval. PASS publishes unchanged reviewed delivery content and closes with the same approval; FAIL or an unresolved verdict holds only that delivery. Source, plan, evidence or reviewed-file drift requires a fresh candidate. Unrelated sibling target advances retain approval only when reviewed files and their recomputed merge content stay unchanged; shared append-only changelog and generated bundles are exempt. When a target move touches reviewed files but the patch the merge adds, with its three lines of surrounding context, keeps its patch-id, the approval is rebound to the new candidate with a receipt and no verifier runs. Tier zero and batch tier one exemptions remain unchanged. A reviewed correction must itself land before close, and its delivery follows the worker's pushed fix branch. Duplicate CI checks at the same SHA use the newest completed conclusion. An override never closes automatically.
- **Retired worker review** - Tier two enforcement deliveries keep their own verifier and adversarial probe after their worker retires. A live supervisor closing an already merged delivery owns the recovery dispatch; only an explicit, recorded supervisor override waives review.
- **Verifier timing** - Verdicts record milliseconds and their source. Dispatched child runtime uses persisted capability bind/consume timestamps; supervisor-direct duration falls back to the dispatch-to-verdict window, including review wait. Explicit duration overrides remain distinct; old timings remain unknown.
- **EPIC READY** - a deduplicated action sent to the epic's live owner once every child task, including those of an accepted split, is closed.
- **Journey registry** - a project's `docs/qa/journeys.yaml` (drafted by `cas qa journeys --seed`): each user journey's owner files, specs, surfaces and live, dark or dead status. Cassy's Commander registry preserves import and CSS selector coverage, with enforcement declared in the tracked registry.
- **Journey impact** - which journeys a diff or delivery touches, the evidence each needs, and the files no selected journey represents; a file stays listed as unowned when semantic selection excludes its registry owners. Journeys rank by traffic share.
- **Journey traffic** - Commander counts each journey's defining act locally and reports the per-day totals only to the operator's paired machines; `cas qa journeys --traffic` turns them into per-journey shares.
- **Upkeep gates (G1-G9)** - park refuses until the journey registry, regression case, CODEMAP and this overview are updated or a reasoned decision is recorded; release notes wait for the post-release check.
- **Hotfix fast lane** - a project that sets `[fast_lane]` merges a small frontend-only bug fix (paths, size and Tier 1 measured from the diff) after its own pre-merge verifier PASS and named merge checks, without a batch release wait; hermetic e2e, the production build and the journey walk become a post-merge receipt that blocks close, one failed check is rerun once, and a failure the hotfix caused opens a revert PR. A failed QA walk asks the operator in Commander to Revert or Fix-forward, with Revert as the fifteen-minute default (`docs/qa/fast-lane.md`).
- **Rapid response mode** - the operator opens a time-boxed window (at most 12 hours) for one epic with `cas qa rapid-response`; while it is open, per-task independent QA, unsampled verification, untouched-route journeys and the batch receipt wait are skipped, while the post-release check stays a full gate. Build and touched-test proofs still refuse; a change with a secret-shaped line or an unreadable diff keeps every gate; migrations keep every gate and need the operator's review; and each skipped check becomes a back-fill task when the window closes.

- **Factory CI coverage** - every factory push validates the delivery from its shared epic fork, so a docs followup cannot cancel a code run and skip its checks. Other events retain their event deltas.

- **Model evaluation proof** - tasks and phases can require numeric evaluation targets on a declared dataset. A passing receipt binds a saved evaluation artifact naming the command, model and measured values to matching machine-readable run-log measurements; both files must resolve within the owning task artifacts directory. Missing prerequisite proof asks for a fresh receipt; a miss stays open and close names its failed bar.
- **Phase outcomes** - an epic or gate can carry numeric targets and evaluation receipts. Missing or missed targets hold dependent starts, closes and merges, including children of dependent phases. Independent work and sequential implementation children continue without waiting on their own phase target. Only an operator decision with a reason accepts a miss, and new measurements require a fresh decision.
- **Gate preflight** - task start lists what close will check for this task and project, and a refused park reports every failed gate in one reply.
- **Rule lifecycle** - A projection receipt outside `.claude/rules` makes deletion durable: a previously generated file removed from the repository retires its stored rule. The shared store opener records the rules active when receipt tracking starts, before any Cloud or hub pull; a fresh database records an empty cut. Those older active rows with absent files are held locally, excluded from prompts and sync, until an explicit `rule action=restore` or `delete` decision. Later Cloud or team arrivals project normally without echoing into the push queue; corrupt per-rule receipts count as missing evidence, and an unreadable start marker is an empty cut. `rule action=list` identifies store, repository and personal-pattern sources. `rule action=create scope=global` with authenticated operator provenance and `stakeholder_quote` creates an immediately active cross-project personal pattern using those exact words, without a project draft or promotion step.
- **Rule references** - code and tests written because of a cited stakeholder rule carry its id and verbatim scope. Close checks each declared causal site and coverage of every cited stakeholder rule; process-rule citations need no marker; verification checks omitted sites. `cas rules refs <id>` lists tracked markers without changing rules or source. Retiring, superseding, un-attributing or re-scoping a rule, or its stakeholder review date passing, files one linked cleanup chore listing the affected markers; nothing is deleted.
- **Review tiers** - close classifies a delivery by the paths it changes and records the tier on the task. Docs and tests have no independent verifier or QA journeys; most changes get one verifier and their impacted journeys; guard, CI, release and close-gate changes also need an adversarial probe. Verifier improvements stay in the verdict unless they show a reproduced defect affecting someone today, and `cas qa polish --epic <id>` lists them by file at release prep. `task create` and QA's automatic follow-ups enforce that with `repro` and `affected`, and an epic's loop gain, follow-ups from findings per completed review, shows in `epic_status` and notifies the supervisor at 0.5 once the epic has 5 completed reviews.
- **Plan conformance** - the verifier reads the epic's referenced plan and reports `PLAN-FIT` against the delivery's assigned scope and outcome targets. Missing planned fields or a missed target reject even when the task card passes, with a supervisor decision about restoring scope or obtaining an authorized plan revision. Unreadable plans or ambiguous scope require a supervisor decision before approval; a child is checked against its planned slice, and an epic against its assembled outcome.
- **Model-owned plan boundary** - A plan can reserve paths or concerns for model judgment. Added literal collections, regexes and exact-string assertions produce named review sites; new meaning-matching code in the reserved area blocks unless the approved plan allows it.
- **Friction ledger** - an append-only record of every check, supervisor intervention, escape, release, feature verdict and identified Cassy problem, written automatically by the code path that saw it. Filing the problem is the write: a bug task in the Cassy repository, or an issue filed through `system action=report_cas_bug`, becomes a friction row, and the report's "Friction found" section shows each one as open, in progress, fixed in vX or closed. `cas ledger backfill` imports earlier Cassy bug tasks and, through a bounded `gh` call, issues on `issues.components.cassy`; friction rows stay local until Cloud accepts the kind. `cas ledger report --release vX` prints the numbers per release across a team's projects; only metrics, timings, titles and links reach Cloud. Backfill recognizes retained legacy queue-ejection aliases before appending a canonical row, preserving one fact per task, PR and failed run.
- **Acknowledged delivery** - a message counts as delivered only when the recipient's session receives it; idle recipients get bounded wakes and the sender is told after five minutes.
- **Supervisor input** - verified paired-device Commander text can steer a running Codex turn. Other message origins keep their wake policy during tools and idle states, including oversized messages; gated rows remain readable through the inbox. Native confirmation dialogs and operator drafts keep incoming text pending.
- **Director wakes** - supervisor director prompts have a durable queue identity and director source attribution. They honour busy turns and protected drafts; non-green delivery decisions retain their original tip, declined tips become superseded notices, and merged alerts are withdrawn after a queue delay.
- **Peer messaging** - published artifact attachments retain the owning task and sharing project and print a scoped fetch command; older pointers ask for a fresh share or task id. Supervisors reach each other by name, project, `project@machine` or `supervisor:<project>`; a message to an ended session goes to its live successor. Untyped peer mail wakes an idle peer without creating a merge hold. Only explicit `kind=ask` messages hold a merge naming that task or PR, until a later message from the same peer reaches the asking supervisor; only explicit receipts and `wake=false` stay in the inbox without waking. Legacy untyped mail keeps its wake behavior, and unknown kinds are refused. CI, task and merge waits use events; plain time reminders are accepted as a backstop.
- **Worker isolation** - on Linux, workers cannot read operator credential stores such as Neon and Vercel, and see only the connectors an operator grants a dedicated worker account.
- **Memory, Rule, Skill** - durable facts, versioned instructions that sync into agent harnesses, and procedural playbooks agents load for a kind of work. Superseded memories expire and leave session context. Only operator-authorised rule writes create encoding chores; agent and supervisor writes name the operator command and leave existing chores intact. Stakeholder rules retain verbatim words and scope; `rule action=drift` reports differences between source, generated files and an explicit peer snapshot without changing policy. Session start restores the current role's handoff and checks its named Slack channels and threads through Violet for newer human posts. Author-labelled excerpts appear above the handoff; bounded reads leave a notice when unavailable or incomplete. Explicit memory/search tools and task-create related context retrieve prior knowledge.
- **DESIGN.md first** - every report, page, chart, note, UI, terminal output, drawing or image an agent produces wears the target project's `DESIGN.md`; a project without one gets one through `design-spec`, and the task records which file and revision it used.
- **Knowledge page** - a distilled, source-linked page about the current repository; the code index connects symbols to that context.

- **Cross-machine approvals** - a confirmed published candidate shares its original approval through the authenticated project peer mailbox. The receiving daemon validates the supervisor, delivery and landed Git tree, then keeps the proof in its existing verification records so the worker can close after mailbox acknowledgement or source-machine cleanup. Changed candidates, foreign senders, non-approved verdicts and replay into a new proof cycle cannot grant authority. Peer failures never fail confirmed publication; permanent receipt refusals are acknowledged as rejected while availability failures retry.

- **Hosted queue precheck** - `cas release precheck <sha>` validates an exact commit on hosted CI and records its run; `--status` reports results and elapsed time. A supervisor's parked merge refused for pending CI resumes automatically on green for the authorized source, repository and target. Terminal CI evidence or a moved lane sends one notice, and pending retries expire after two hours. A landed merge preserves a held close as a follow-up. The precheck isolates Python imports, recovers uncertain dispatches without sending another run, reports JSON errors and deletes completed precheck refs only at the expected SHA.
- **Queue archive dependencies** - hosted Rust suite builds restore a compatible main-scoped dependency cache while compiling current source. Advisory main priming fills a missing cache after queue-proof reuse; it adds no required check, and disposable queue refs do not save dependency copies.

- **Epic design review** - five Bug tasks labelled `stakeholder-reported` at P0/P1 within 48 hours pause new starts and spawns on their epic. The supervisor reviews the design against the plan; the operator resumes staffing with a recorded reason. Configurable thresholds, acknowledged reports and per-epic scope keep other work and shipping available.

## Primary Journeys

Completed native Claude, Codex and Grok turns mirror into durable Commander history, including answers to questions typed in the terminal. Long key-shaped credentials are redacted while ordinary hyphenated words stay verbatim. Grok text streams appear only after native turn completion; thoughts, text before tool calls and cancelled turns stay out of the reply. Native synthetic prompts never become operator questions, and text/image chunks in one pasted prompt keep the answer linked to that question. OpenCode transcript mirroring remains unsupported.

Commander omits unsolicited supervisor replies that only acknowledge a message or say there is no action. Direct answers, substantive status updates and native Claude API errors remain visible; a failed turn appears in the conversation and session preview without waiting for another turn.

Claude factory launches prefer the native installer’s active binary, then its newest installed version, then PATH. Commander checks the same executable before launch. Each launch verifies Claude Code 2.1.280 or newer and refuses with the detected path and version when no compatible client is available. Hub service status gives missing, outdated and unverifiable Claude clients their own install, update or repair action; missing clients remain not installed in doctor and the account picker.

Commander labels each machine's reported Cassy version in its project chip and paired-machine card. A newer published stable release adds a quiet update note; an hourly cached lookup retains its last known release while offline. The Web footer separately identifies the client release and build. Each online supervisor with a known MCP version also shows its own version badge; an upgrade arrow marks a supervisor running an older Cassy than its machine has installed, with reconnect guidance. Unknown versions stay unreported.

Commander lists running conversations only. Ended and crashed sessions leave navigation without dismissal or attach retries; empty project cards disappear. A machine outage keeps its last-known running conversations while recovery is shown at machine level. Waiting messages to a confirmed stopped session become Not sent, with their words available in Saved messages; running replacements return without a reload.

Project cards keep the Most recent badge on the same session while sibling activity alternates within a whole minute, using stable session identity to break ties. Activity in a later minute moves the badge without shifting rows.

The operator can paste text, screenshots or files into Commander: long text becomes a previewed text attachment, and Send stores files on the session's machine and gives the supervisor readable local paths through the existing durable message lane. Pending files remain through reconnect, with a reminder to send before closing the page. The operator's own sent files appear in their bubble as image previews and named file chips after reload and on other paired devices, without displaying host paths.

The composer also offers a local, lazily loaded emoji tray beside the mic: search or choose a recent emoji, replace the current selection and continue the same draft. Messages, previews and waiting questions preserve Unicode text while selecting native color-emoji fonts.

   In batch mode, a later exact release verdict also clears an expired Tier 1 dispatch and deferred batch debt. Its receipt is acknowledged once recorded; delivery closes that exceed the response grace continue through the ordinary gates, with each outcome retained as a bounded task-note summary. Batch, post-commit and late-close system summaries cannot cite producer evidence. Long close remedies are retained in immutable receipt files with complete pointers in their summaries. Restored and synced producer citations get their own timestamped note, and another covering receipt adds no outcome note to an already-closed task. A new supervisor receives integrated project deliveries across all review tiers as close actions with current holds at startup, independently of the retired session's handoff preview. Unreadable verification rows are skipped and reported without losing the inherited handoff or other recovery rows. It names a retired folder that came back. `cas doctor --fix` repairs link drift, and `--yes` backs up and replaces real items.
9. The operator invokes the builtin `finish` skill (`/finish` in Claude Code) to stop the background work it started, clean up session work and save a handoff and learnings; a handoff that names each task the session still holds lets it end with those tasks left open; updates distribute it across harnesses while preserving personal overrides. From Commander, `/` in the composer or the header command button offers curated Claude/Codex controls under a paired input lease (HUB-J27). Clear, Exit and Finish confirm. Finish queues until the native turn ends and its prompt is empty; background shell footer output does not keep an idle supervisor busy. Exit and Reload Cassy use the same native turn completion signal while retaining empty-prompt, draft and modal checks. Claude local-command transcript entries do not start a model turn and appear as compact terminal receipts in the thread and preview. Receipts distinguish queued, submitted, observed and uncertain outcomes, and the Finish reply mirrors to the conversation. Finish names a completed harness request, while Exit follows the authenticated session-ended receipt. Usage recognizes Claude’s session-cost and quota views, and an uncertain Usage receipt retains Close so the operator can return to the prompt before sending again. Claude supervisors offer Reload Cassy directly on a card whose MCP is older than its installed binary, and through Session actions or typed `/mcp`. The existing command reconnects their managed MCP server and confirms its replacement PID and version from the registry. The header slash button opens its dropdown beside the button; command status can be dismissed without cancelling a pending command, and accepted retries replace earlier refused busy rows. Other harnesses receive a named refusal; the owning daemon must already contain the action.

In Commander the operator turns on Show work to see the supervisor's thinking, tool calls and task moves between its replies, collapsed until opened, and opens a worker's live timeline from Tasks & progress instead of watching its terminal (HUB-J25); on a phone it is a bottom sheet whose note keeps the worker's name whole and whose buttons align with the note's text. Typed tool rows name reads, searches, commands and edits with their reported scope; opening one shows its targets or command metadata alongside the exact tool record. Failures are named, and unfamiliar tools retain their raw text. The daemon reads these from existing transcripts and the task DB with zero model tokens, and pushes a contentless change notice to clients that read a page. Tasks & progress leads with focused-release merged/total, merges per hour and last merge, and groups tasks from the supervisor's open epics as Needs you, In progress and Ready with All tasks available. Its desktop width is adjustable by pointer or keyboard and remembered per browser; permission guidance replaces unavailable header controls.

11. In Commander the operator reads safe Mermaid diagrams, expands unified diffs, and inspects inline image, video, audio and PDF first-page attachments. An image card opens a zoomable, pannable gallery of that turn's images, names loading failures, and returns focus and reading position on close (HUB-J4). Fenced source has a language or filename header, Copy with visible success or failure, and a per-block Wrap toggle for phone reading. Source and original files remain reachable; previews reserve their space and rich renderers load on demand.

12. A supervisor attaches an HTML page, such as a report with diagrams, images or video, to a reply, and Commander shows it inline beneath the file card, in the conversation's light or dark theme, and opens it in its own tab (HUB-J4). The publishing machine serves the page through a short-lived ticket under a CSP sandbox: no script, an opaque origin, no top navigation or popups, no network beyond its own assets, and framing allowed only from the Commander origin that asked. Agent markup never enters Commander's document.

Factory turn costs are recorded locally for Claude, Codex and Grok supervisors and workers, independently of Commander mirroring. `cas ledger report --release vX.Y.Z --offline` reads release-window ledger rows to show wakes, no-op wakes, input/output tokens and minutes by channel, with counts for missing measurements. Wake channels come from authenticated queue provenance, including a session-less daemon row addressed to that exact agent. Without a row, a Claude background-task notification counts as the agent's own role, CAS's fixed worker startup and delivery-watchdog texts count as daemon, and any other input counts as terminal (unauthenticated pane input). A no-op means no successful supported action was observed. Prose counts as an answer only for an authenticated operator wake or a question verified against its authenticated queue row; Teams wrappers and pointer wakes use the original row provenance, and launch-context messages do not take the wake slot. For other wakes, only typed tool actions count: task, coordination and edit writes, factory and verification writes such as merges and spawns, and subagent launches. Reads, waits, receipt-only replies and status restatements do not count. Shell actions are conservatively recognized only for explicit commit, push and check commands, including the patches and commands inside a Codex code-mode `exec` script. OpenCode turns are not recorded yet. Unsupported Cloud Turn events remain queued locally behind their own push cursor and six-hour kind cooldown; other ledger kinds keep pushing, and every sync round attempts pull even if push fails.
