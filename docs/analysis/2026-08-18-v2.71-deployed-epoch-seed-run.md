# v2.71 fix-wave seed run — executed against the epoch-capable database

M3 (`deployed_epoch_verdicts.py`, cas-c214) shipped its renderer but deferred the
real v2.71 seed run, recording that the live database had no `history_epochs`
table. That measurement was taken against the wrong database. This run executes
the deferred seed set against the right one and records what it actually found.

## The deferral premise was wrong about which database

| Database | Size | `history_epochs` |
|---|---|---|
| `~/.cas/cas.db` (global store: entries/rules/sessions) | 176 KB | **absent** — `Error: no such table` |
| `/home/pippenz/Petrastella/cas-src/.cas/cas.db` (project coordination DB) | 631 MB | **1360 rows**, all `epoch_kind='daemon_start'` |

The M3 refresh instructions themselves said `--epochs-db "$HOME/.cas/cas.db"`,
which is the store that cannot answer the question; that line is corrected in
`2026-08-17-deployed-epoch-verdicts.md` as part of this change. Every seed in
this run loaded all 1360 epochs (`epochs_considered: 1360`,
`epochs_without_binary_identity: 0`).

## What was run

```bash
# 1. M1 units → M3's evidence contract (exposure denominator; NOT term-filtered)
python3 docs/analysis/scripts/seed_evidence_inputs.py evidence \
  --units-db /home/pippenz/.cas/artifacts/cas-b78b/evidence/units.sqlite3 \
  --since 2026-08-01 \
  --output   ~/.cas/artifacts/cas-2332/evidence.json \
  --output-manifest ~/.cas/artifacts/cas-2332/evidence-manifest.json

# 2. M2 semantic candidates per seed, mapped onto M1 unit ids (review artifact)
python3 docs/analysis/scripts/seed_evidence_inputs.py candidates \
  --seeds docs/analysis/v2.71.0-fix-wave-seeds.json \
  --units-db /home/pippenz/.cas/artifacts/cas-b78b/evidence/units.sqlite3 \
  --index /home/pippenz/.cas/artifacts/cas-2556/operational-index/index.sqlite3 \
  --top 15 --output ~/.cas/artifacts/cas-2332/semantic-candidates.json

# 3. The seed run itself, against the epoch-capable DB
python3 docs/analysis/scripts/deployed_epoch_verdicts.py \
  --seeds docs/analysis/v2.71.0-fix-wave-seeds.json \
  --epochs-db /home/pippenz/Petrastella/cas-src/.cas/cas.db \
  --evidence ~/.cas/artifacts/cas-2332/evidence.json \
  --output-json   ~/.cas/artifacts/cas-2332/v2.71-deployed-epoch-verdicts-lexical-only.json \
  --output-report ~/.cas/artifacts/cas-2332/v2.71-verdicts-lexical-only.md
```

Evidence corpus: **17,119** M1 units first observed between 2026-08-01T02:16:56Z
and 2026-08-18T13:10:50Z. 6 units were excluded because a later authority
withdrew their claim; 6,243 fell before the `--since` cutoff. The corpus is
deliberately not filtered by any fix's terms — M3 derives *exposure* from it,
and filtering would shrink the denominator that decides whether a clean-post
window was observed well enough to call anything fixed.

## Result

**Deployment boundary.** Every seed in the wave was built between 2026-08-15 and
2026-08-16, but the daemon did not start running the 2.71.0 binary until
**2026-08-17T13:12:34Z**. For 19 of 20 seeds `fix_started_running` equals
`clean_post_from` with `overlapping_nonfixed_epochs: 0` — no mixed window at
all. This is the merge-versus-epoch trap M3 exists to make visible: a fix
"landed" on Aug 16 was not *serving* until the following afternoon, and any
symptom in between is pre-fix evidence.

**Exposure.** 15,666 clean-pre and **1,453 clean-post** observations per seed,
against a required threshold of 100. Post-fix observation is 14× the bar.

**Symptom matches.** Three lexical matches fired across the whole wave —
`cas-d3a3`, `cas-dcf2`, `cas-epic-base` — and **all three are `clean-pre`**
(2026-08-16T04:32Z–13:42Z, before the fixed binary was serving). Zero clean-post
symptom matches for any of the 20 fixes.

**Verdicts: 20 × `insufficient-post-fix-data`.** Not because the evidence is
thin — it is not — but for exactly one reason: `M2 semantic evidence has not
been evaluated for this fix`. With adequate exposure and no clean-post symptom
match, the only thing standing between these 20 fixes and a `fixed` verdict is
the human labelling step. That gate is M3 working as designed; the honest
statement today is "no observed recurrence, fix confirmation pending review".

## Findings for the owners of M2/M3

1. **The semantic map cannot say "reviewed, nothing matched".** *(Fixed — see
   [the M4 writeup](2026-08-18-memory-contradiction-queue.md).)* M3 read
   `semantic.get(fix_id, {})` and treated an empty map as *not evaluated*, so a
   fix whose candidates were all reviewed and correctly rejected was
   indistinguishable from one nobody looked at and could never reach `fixed`.
   The contract now accepts a declared evaluation
   (`{"evaluated": true, "candidates_reviewed": n, "reviewer": ..., "scores": {}}`)
   alongside the original bare map, which still means *not evaluated* when
   empty. The first real `fixed` verdict on this machine came out of that
   change. Re-running the 20 v2.71 seeds through it needs their candidate pools
   labelled; that labelling is still open.
2. **M2 retrieval scores are not on the seeds' threshold scale.** A real hybrid
   query returns scores around 0.03 while the seeds declare
   `semantic_threshold: 0.8`. Feeding raw scores through would silently disable
   the semantic channel *and* release the "not evaluated" guard — the worst
   combination available. `seed_evidence_inputs.py` therefore requires explicit
   labels carrying their own confidence, and refuses to pass retrieval scores
   off as similarities.
3. **The two corpora only partly overlap.** 7,826 of M1's 32,773 units share a
   `content_hash` with an M2 event (of 46,654). Of the 300 top candidates this
   run pulled (15 per seed), only **64 (21%)** map onto an M1 unit and can
   therefore ever become M3 evidence; the other 236 are visible to M2 but
   invisible to the verdict path. Any claim about semantic coverage has to be
   stated against that 21%, not against M2's full index.
4. **M1's snapshot predates the current epoch.** The evidence artifact was
   ingested from a snapshot taken 2026-08-18T09:11Z, before the 2.72.0 daemon
   started at 12:53Z. It fully covers the v2.71 clean-post window, so these
   verdicts stand; a v2.72 wave would need an incremental re-ingest first.
