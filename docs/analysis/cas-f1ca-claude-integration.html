Claude integration research for Cassy 3.64

Keep task authority in Cassy; adapt native execution.

Research cutoff: 17 October 2026, 21:30 UTC. Cassy source: 5e4774024045f19adaddf8da0e7ac1e69d19a9ad. This is a recommendation, with high confidence in the documented distinctions and source mapping, and no new runtime validation. It creates no dependency on the 3.63 release.

Recommendation

Prefer the existing backend and delivery adapters, with canonical role content projected into each supported native format and capability evidence bound to the actual launch. Keep assignment, task start, durable messages, verifier dispatch and independent QA in Cassy. A native role, task, goal, permission approval or successful write to a transport does not grant that authority.

Layer Existing Cassy seam Recommended responsibility
Authority Task lifecycle, verifier and QA services Assignment, leases, authenticated dispatch and reviewed-tip acceptance
Native execution Backend, role assets, hook encoding and delivery adapters Harness-specific fields, modes, launch prerequisites and transport
Evidence Conformance receipts and delivery observations Version, channel, effective policy/trust, loaded behavior and actual turn; missing facts stay unknown

This is a preferred structure under Cassy's existing constraints, not a measured claim of the fastest or cheapest implementation.

These are qualitative engineering judgments, not estimated costs or benchmarks.

Why this one

The deciding criterion is preserving durable authority while using supported native capabilities. Three independent source-only proposals converged on that criterion: a narrow delivery interface; shared role delivery for ordinary launch and asset reconciliation; and separate launch, hook and proxy policy contracts. Their useful parts fit existing modules. They do not justify one universal engine or a new connector option whose every use would fail.

Backend already varies launch and cancellation behavior (crates/cas-mux/src/backend/mod.rs:58); HookOutput owns differing wire shapes (crates/cas-core/src/hooks/types.rs:49); proxy policy authorizes before forwarding (crates/cas-mcp-proxy/src/lib.rs:1430). Keep those responsibilities separate. The existing verifier body macro demonstrates shared content with native tool-name projection (cas-cli/src/builtins.rs:62).

A common caller should describe an assigned operation and required safeguards, not construct native JSON, socket paths or role frontmatter. Reuse existing launch inputs and conformance records before adding interfaces. A future role delivery plan can share the canonical body while reporting unsupported native fields; delivery should accept a durable message ID and return the observed attempt/evidence. Do not combine launch, account selection, message delivery and authorization in one module.

For example, an already-assigned task requests a specialist through the existing backend with its resolved model, tools and workspace. The native adapter prepares the appropriate role assets and launch. Successful loading is evidence only; a child owning assigned implementation work still needs its genuine CAS identity and authorized task start. A task-verifier needs its separate sealed dispatch. Bounded research delegation can remain within the parent's task ownership. A message reply updates delivery evidence without changing task ownership or independently closing work.

The deletion test is concrete: a shared role projection earns its place only when deleting it redistributes body/tool-prefix/field/migration rules into both sync and launch callers. A delivery seam earns its place only when it removes duplicate generation, hold, retry and receipt logic from actual callers. A wrapper around one function or a speculative connector registry does not.

What we give up

The strongest alternative is native-first orchestration: teams, workflows, goals and streaming sessions can reduce manual prompt and context plumbing. That is a useful pilot hypothesis for bounded work. It also inherits native replay, feature rollouts, scope-dependent fields and session persistence. Keep its potential benefit separate from an unmeasured speed/cost claim and from CAS assignment or independent review.

Reversal cost

Preserve the current backend and durable records while a native adapter is evaluated. Disable a new execution route without moving task ownership, rewriting live profiles or converting the queue. Keep canonical role bodies and managed-file provenance so an adapter rollback preserves user customization. Moving durable ownership into native tasks would make that reversal materially harder; no such migration is recommended.
