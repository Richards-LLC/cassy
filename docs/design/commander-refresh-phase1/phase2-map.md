##6e3a roster binding

Peer `progress-model.ts` provides `WorkerProgress { name, agent?, currentTask?, work }`. Preserve these exact distinctions:

- `session.workers === undefined`: may fall back to reported non-supervisor agents. `session.workers === []`: zero workers, never fall back. Deduplicate by exact name and exclude supervisor by identity/role.
- `agent.current_task` has an ID and matching task: show that task title and human `statusLabel`. An ID without task details says **Task details not reported**, retaining the ID.
- Explicit `current_task === null`: **No current task**. Missing agent/current-task field: **Current work not reported**, never idle/healthy. A raw last-note sentence must never replace these values.
- `statusLabel` normalizes human status spelling; it is not a liveness evaluator. In progress alone does not prove fresh work, and task Blocked alone does not mean Needs you.
- Sparse metadata can display all six catalog workers while authorizing no synthetic fleet controls. Aggregate work counts must not treat unknown roster members as idle or busy. Unvisited conversations often have catalog activity but no loaded status/summary; show the honest fallback, avoid a new every-row polling loop.

Read6e3a QA correctives before implementation: HUB-J17 roster fixtures must supply the actual selected session roster, not just status.agents, and Send-for-review contrast must use paired action foregrounds. A source-only peer brief is not proof its final visual/fixture issues are resolved.
