## Primary Journeys

Reload Cassy works for Claude and Codex supervisors, from the card, the command menu, `/mcp` or `/reload-cassy`. It first reads the live MCP process: when it already runs the installed `cas --version`, Commander shows its loaded-build badge and sends nothing. Otherwise the reload waits, with a small animation, for the supervisor's turn to end and its prompt to be empty, so a running tool call is never interrupted. Claude reconnects with `/mcp reconnect cas`. Codex has no MCP reconnect, so after a one-line confirmation its supervisor restarts on the installed build while workers keep running. The in-place MCP front cannot replace this: it refuses a backend swap whose tool schemas differ from the harness's initialized catalog, which nearly every release changes. Success requires a replacement live MCP process whose version equals the installed build; a mismatch or timeout names the next step. The supervisor card, the open conversation's header and the factory status bar then show the loaded build and its Eastern load time, for example "cassy 4.52.0 · loaded 5:44 PM ET", read from the live process until the next reload. Command receipt writes take their own short wait budget, so a brief database hold no longer turns a working reload into a failure.
