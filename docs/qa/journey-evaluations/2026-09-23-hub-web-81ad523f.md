## Findings

### F1 — High — The command palette filter does not filter (HUB-J3, stage 3 "Jump to a supervisor by name")

- **Receipt:** HUB-J3 `journey.webm @09.5s` (frame f020) and `trace action 42/43`. The snapshot after `Fill "calm-otter-4"` still lists all 11 commands. The on-screen list has only scrolled, so "Appearance · Dark", "Terminal workspace", "Workers · Hidden" and the others stay visible, and "Jump to calm-otter-4" is the last row.
- **User experience:** The user types a supervisor's name, and nothing narrows. With two sessions the target is still on screen. With the real fleet (tens of sessions and workers), "find by name" means scrolling through every command. Enter does pick the right row, because the JS reads the `hidden` property, but the screen does not show that.
- **Likely cause:** `main.ts:2773` sets `command.hidden`, but `.palette-command { display: grid }` (`styles.css:2006`) overrides the user-agent `[hidden]` rule.
- **Fix:** Add `.palette-command[hidden] { display: none; }`. Show "Jump to …" matches first when the query matches a session. Add a journey assertion that commands that don't match are not visible.
- task: cas-45c3

### F2 — High — The pair link makes the user retype what the machine already knows (HUB-J2, stage 2 "Confirm the machine and pair")

- **Receipt:** HUB-J2 `01-open-the-link-the-machine-printed.png` and `journey.webm @04–06s` (the user fills in "https://atlas.test" and "Atlas · Linux"). The link carries only `hub=atlas` (`pair-link.journey.ts:12`).
- **User experience:** The machine prints a link to click. The dialog then asks the user to type that same machine's hub address and a name for it. The helper under the field is three lines of technical text ("…usually its Tailscale name. It is not this page's address unless this page is served by that machine"). A "Use this page's address (http://127.0.0.1:4792)" control is styled like a code sample, not a button. That is three typed fields (address, machine label, operator label) on the "no extra click" path.
- **Fix:** Have `cas hub pair` put the reachable hub URL and the machine's display name in the fragment, and prefill both as editable values. Move the address guidance behind a "Where do I find this?" disclosure. Style the "use this page's address" control as a secondary button.
- task: cas-bd2fe

### F3 — High — The pairing dialogs speak in internal terms (HUB-J1, stages 2–4; HUB-J2, stage 2)

- **Receipt:** HUB-J1 `journey.webm @04.5s` (f010, the create step), `02-ask-for-a-pairing-code.png`, `03-approve-on-the-machine.png`, and HUB-J2 `01-open-the-link-the-machine-printed.png`.
- **User experience:** A first-time user reads "Email code (optional)" above a field whose placeholder is an email address. They also see "CASSY CLOUD ORIGIN http://127.0.0.1:4792", "EXACT SCOPES machine:read, session:read, pane:read, pane:input, message:send, pane:interrupt" (shown twice, on the code step and on the confirm step), "create this browser's device credential" and "Confirm the target hub". The confirm step asks for both "Device label" and "Operator label" without saying how they differ. The plain-language line ("Read sessions and terminals · Type, send messages and interrupt") is present, but the jargon around it buries it.
- **Fix:** Lead with the plain "This browser will be able to" sentence. Collapse the origin and raw scopes into a "Technical details" disclosure. Rename or explain "Email code". Relabel the fields "Your name (shown on the machine)" and "Name for this browser". Replace "device credential" with "save access for this browser".
- task: cas-583b

### F5 — High — Sent and delivered look the same (HUB-J5, stages 2–3)

- **Receipt:** HUB-J5 `02-write-and-send.png` ("Sending…" in the bubble; the composer status reads "Sending to patient-pelican-9 · awaiting receipt") and `03-see-it-delivered-and-answered.png` (the bubble shows no status at all).
- **User experience:** Once the message is delivered, "Sending…" simply disappears. Nothing says "Delivered", so the only proof is the reply arriving. If the supervisor is slow, a delivered message and a lost one look identical. "Awaiting receipt" is protocol vocabulary. The catalog expects the user to "tell sent from delivered without reading attributes".
- **Fix:** Show "Delivered" (a check plus the word) under the latest delivered message until the reply lands. Reword the composer status to "Waiting for patient-pelican-9 to confirm…".
- task: cas-58d0

### F6 — High — A refused message has no useful reason and is left behind after the fix (HUB-J5, stage 4)

- **Receipt:** HUB-J5 `04-a-refused-message-can-be-edited-and-resent.png`, `journey.webm @12.0–13.5s`, and `final.aria.yml` (the log still holds "Not sent · Permission refused" with "Edit message" and "Retry sending" after the edited message was sent).
- **User experience:** The bubble says "Not sent · Permission refused", and the composer says "Message rejected by the hub: Permission refused". Neither says whose permission or what to do next. After the user edits and resends, the refused bubble stays in the thread with live Edit and Retry buttons, so one tap on Retry sends the text that was just corrected. While the message is refused, the list row preview reads "You: Ship it without the gate." as if it had been said.

Once an edited version is sent, collapse the refused bubble to "Not sent · replaced by your edit" and remove Retry. Leave unsent messages out of the list preview, or prefix them "Not sent:".
