### F26 — Normal — The list header wraps onto a second row on every screen (HUB-J1–J13, all list stages)

  | HUB-J9 | 390 px | light | `J01.png` |
  | HUB-J13 | 390 px | light | `J01.png` ("Allow new sessions"), `J02.png` ("+ New session") |

- **What the user sees:**
  - "Conversations" now sits alone on its row.
  - "Allow new sessions · Pair a machine" sits on a second, right-aligned row. It looks detached from the heading and splits the heading from its tagline.
  - The search field and the list start about 35 px lower. On HUB-J8 `J10.png`, the fourth row (gabber-studio) is now cut off at the footer, with its "Live" line hidden.
  - A 1280 px screen gains nothing, because the sidebar is about 374 px wide there too.
  - Nothing clips or overlaps.
  - When the first machine arrives, the heading grows from one row to two and the page shifts (HUB-J9 @0:01.6 → 0:01.8).
- **Cause:** `conversation-shell.ts:302` puts both buttons in `.conversation-list-actions` inside `.conversation-list-title`. The CSS then wraps them:

  - `styles.css:3876` sets `margin-inline-start: auto`.
  - The content needs about 430 px. The space available is about 338 px at 1280 and about 366 px at 390.
  - The shorter "+ New session" label wraps too.
- **Fix:** keep one control beside the heading.
  - Either move the actions into `.conversation-list-top` next to the appearance icon, or move "Pair a machine" to the footer machine chip and keep only "+ New session".
  - Add a journey assertion that the h1 and its actions share one line at 1280 and 390.
- task: cas-865c

### F27 — Normal — "Allow new sessions" is a permanent, unclear control in the header and the palette (HUB-J1 stage 4 onwards, J2 stage 4 onwards, J3, J5, J8, J9, J13 stage 1)

- **Receipt:** HUB-J1 `J04.png`, HUB-J2 `J04.png`, HUB-J9 `J01.png`, HUB-J13 `J01.png`. In every `final.aria.yml` from a default pairing, `button "Allow new sessions"` is read before "Pair a machine". The palette's Machines group reads "Allow new sessions — Let this browser start sessions" (HUB-J8 @1:41).
- **Who sees it:** a default pairing never grants the permission to start sessions (`pairing-scopes.ts:7-15`), and `launchAvailability()` returns "grant" whenever machines exist and none has it (`main.ts:974-977`). So every existing pairing, and a first-time user straight after pairing, sees this control on every visit.
- **What the user experiences:**
  - It reads like a switch that acts at once.
  - It uses "sessions" where the list says conversations and supervisors.
  - It actually opens a sheet with a command to run on the machine, and the link that command prints replaces the pairing (`launch-session.ts:262-266`).
  - The palette hint says "this browser", while its neighbour says "other devices".
  - At 390 px it sits opposite the primary "+ Write to a supervisor" button, so the screen offers two "+ something" actions.
- **Fix:** label the control by its goal in both states ("+ New session"), and let the sheet's grant view explain the permission. The HUB-J13 catalog already says "the same place explains how to get it". Put "Pair a machine" first.
- task: cas-865c

### F29 — Normal — Re-pair silently drops the permission to start sessions (HUB-J12 stage 9)

- **Receipt:** HUB-J12 `J09.png`. The Re-pair dialog promises only "Read sessions and terminals · Type, send messages and interrupt".
- **Cause:** Re-pair uses the code flow.
  - The code flow always requests `DEFAULT_PAIRING_SCOPES` (`main.ts:1226`; `pairing-relay.ts:7`).
  - Its response parser rejects any other scope (`pairing-relay.ts:76`).
- **What the user experiences:** a browser that could start sessions is revoked and re-pairs through the offered button. It loses New session without being told, and the header flips back to "Allow new sessions". The only hint is "Its saved access here is replaced…" (`main.ts:642`).
- **Fix:** when the stored scopes include `session-launch`, send re-pair through the link path (`launchGrantCommand`, `pairing-scopes.ts`), or say "Starting sessions will need to be allowed again".
- task: cas-0e14

### F30 — Normal — New session ignores the machine's connection state (code-traced; not on screen)

- **Receipt:** the header control never changes through Reconnecting (HUB-J11 `J02.png`; HUB-J12 @0:25.5–0:31), through Degraded (HUB-J12 @0:15.5–0:25), or under "Needs pairing" (HUB-J12 @1:52.5). In these receipts only the grant state is shown, and its command works offline, so no harm is observed.
- **Cause:**
  - `launchAvailability` (`main.ts:974`) reads only the machine count and scopes.
  - The sheet's machine picker labels machines by scope only (`launch-session.ts:545`).
  - `open()` prefers the current machine (`launch-session.ts:314-320`).
- **What would happen:** with "+ New session" offered, the sheet would open on a reconnecting or unpaired machine. It would fail only after loading, with "Couldn't load … projects" (`launch-session.ts:484`), rather than in the banner's words.
- **Fix:**
  - Pass the connection state into `LaunchMachine`.
  - Suffix the machine options "· reconnecting" or "· needs pairing".
  - Prefer a live machine that can start sessions.
- task: cas-0e14

### F31 — Normal — The grant command breaks mid-word on a phone (HUB-J13 stage 1)

  - Break only after commas and spaces, for example with a `<wbr>` after each comma and `overflow-wrap: break-word`.
  - Say what happens to the pairing once, in one way.
