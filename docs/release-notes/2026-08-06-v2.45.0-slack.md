=== MESSAGE 1 — User thread, top-level ===
Live on production — **User** — A notification that has to wait for you no longer buries you in copies of itself, and a helper that starts from an out-of-date starting point now tells you so.

=== MESSAGE 2 — User thread, reply (to MESSAGE 1 ts) ===
**Was →** when an update arrived while you were mid-task, it sat waiting to be shown — and got re-sent roughly ten times a second the whole time it waited. A single update could turn into hundreds of identical copies stacked through your conversation, and it kept coming even after you acknowledged it and even after the thing it was about had finished. Separately, a helper could be started from a branch that had fallen weeks behind the current work and begin quietly missing everything that had landed since; the only hint was a small number tucked into a status column that was easy to read past.
**Now →** an update is shown once right away and then, at most, once per reminder interval until you respond — and acknowledging it stops it for good. When a helper is about to start from an out-of-date point, you're told up front how far behind it is, what it's missing, and how to bring it current, and status views spell that out in words rather than a bare number. Reviews are also now handled by whoever actually owns them, so a review no longer gets attempted by the wrong party and rejected after the fact. And a heavily-loaded machine no longer reports a false test failure that had nothing to do with the code being checked.

=== MESSAGE 3 — Dev thread, top-level ===
Live on production — **Dev** — Parked lifecycle rows are throttled to one delivery per nudge interval with acknowledgement as a terminal stop, and spawn provisioning now emits a stale-base warning with behind-counts against trunk and remote.

=== MESSAGE 4 — Dev thread, reply (to MESSAGE 3 ts) ===
**Was →** there was only ever one queue row per lifecycle transition; the duplication was on the delivery side. A wake-eligible row was deliberately not consumed until it actually woke the pane, but the queue is polled every ~100ms, so a row that never won the wake was re-selected and re-nudged continuously — two rows parked 6.4 minutes produced roughly 3,800 delivery passes. The inbox content-dedupe only suppressed an append while an identical row was still present, so once the recipient's harness consumed it the next pass appended it again, which is why the storm outlived both an explicit acknowledgement (which set `acked_at`, a field the redelivery loop never consulted) and the close of the referenced task. On spawn, the base ref was never compared against trunk at all — the existing mismatch check only asked whether the base contained the epic tip, trivially true when the base *is* the epic branch — so an epic branch cut before a release merge left every worker 25 commits in the past. And the completion tool's own schema documented the review envelope as something the worker produces, directly contradicting the guides, so the instruction attached to the action won.
**Now →** a pure `lifecycle_redelivery_decision` gates every supervisor-wake row: first sight delivers immediately (no added latency), subsequent passes within the 60s interval are held without consuming the row so an unanswered transition still retries at nudge cadence, and a set `acked_at` suppresses permanently. Per-row bookkeeping keyed by prompt id, dropped on consume/suppress so the map can't leak; the regression test drives 3,600 simulated polls and asserts 6 deliveries. `stale_spawn_base_notice()` compares the resolved base against its own tracking branch, the integration trunk, and trunk's remote, reporting every positive behind-count with SHAs and the remedy into the spawn audit trail and the supervisor inbox (missing refs skipped, so local-only repos stay silent); `worker_status` renders an explicit STALE BASE line. A new `code_review_dispatch` gate resolves review ownership before the skill is recorded and refuses worker invocation under the supervisor-owned default, naming the legal next move — with the schema text corrected and the worker-owned escape hatch preserved and tested. Also: the `orphan_gc` decoy test re-plants rather than panicking when a planted process exits early on a loaded host, with no assertion relaxed, and the recovery reference gained a wedged-test-binary recipe (TIME-vs-ETIME + wchan check, pid-scoped reaping, never-by-name warning) across all three harness flavors.
