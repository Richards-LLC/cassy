## Post 1 — User

Live on main — **User**

Every new conversation used to start by reading your project from scratch — the same files, the same questions, the same slow rediscovery, over and over. Your project can now explain itself: CAS distills your docs and code into a wiki it reads at startup, so a session begins already knowing its way around.

### Reply to Post 1

- **Was → Now:** understanding an unfamiliar corner of a project meant an assistant reading its way there file by file, every single session → one command distills your documentation, README, agent instructions, key configuration and a summary of every code module into a wiki of plain-English pages. `cas knowledge build` writes them; `status`, `list`, `search` and `read` cover the rest.
- **Was → Now:** anything an assistant "learned" about your project evaporated when the conversation ended → the pages are ordinary markdown files on disk under `.cas/knowledge/`. You can grep them, edit them, review them in a pull request, and delete them like any other file. Nothing is trapped in a database.
- **Was → Now:** the startup briefing could only carry memories and tasks → it now also carries a one-line pointer to every page, and the assistant pulls the full text of only the ones your actual question needs. Bodies deliberately never go into the briefing, so an index of fifty pages costs a fraction of what a single body would.
- **Was → Now:** a generated-docs system will eventually overwrite the thing you corrected by hand — that is the whole reason people distrust them → a page can be locked, and a locked page is untouchable from every direction at once: regeneration cannot rewrite it, cleanup cannot delete it, and a teammate's copy arriving over sync cannot overwrite it. Text you write above the first generated section is left alone even on an unlocked page.
- **Was → Now:** keeping generated documentation current meant regenerating everything and paying for all of it → a pass over a project that has not changed costs exactly nothing, because every source is fingerprinted and skipped when it has not moved. Distilling spends model tokens, so it never runs on its own unless you opt in.
- **Was → Now:** search looked only at your memories, tasks and rules → it searches the wiki too, and surfaces pages connected to what you asked about even when they do not share your exact words. Connected results always rank below anything that literally matched.
- **Was → Now:** conceptual searches were quietly throwing away most of their own ranking, so results came back in a subtly wrong order → fixed. Details in the dev thread.
- **Was → Now:** the codemap and project-overview commands each regenerated their document from nothing → they now read from and write back to the same wiki, so the docs you get and the knowledge the assistant retrieves stay one body of text instead of two that drift.
- **Was → Now:** distilled knowledge stopped at your machine → with an account connected, pages sync to your team alongside memories and tasks, and gain semantic embeddings so search matches on meaning rather than only shared words. Logged out, none of that runs and nothing extra is written to disk — your local project stays the source of truth either way.

## Post 2 — Dev

Live on main — **Dev**

Repo context was re-derived from raw files on every session, at full token cost, with nothing persisted between them. This adds a durable distillation layer: an LLM-generated page store with a content-hash ledger, index-inject/body-pull retrieval at SessionStart, an agent-facing tool, and capability-gated cloud embeddings — plus a fix for a ranking bug that had been silently voiding 60% of every conceptual query's weight.

### Reply to Post 2

- **Was → Now:** no persistent representation of repo knowledge existed → a store of page rows plus a blake3 content-hash source ledger and a contentless FTS index. Bodies live on disk as markdown, never in a column, so they stay greppable and diffable. Ingest is one transaction across rows, index, ledger and the tombstone cascade, and bodies are two-phase (stage → publish → rollback-with-restore) — an aborted pass leaves both the database and the knowledge directory byte-for-byte unchanged. Verified by fault injection that forces a real failure *after* the ledger write and asserts all four roll back together.
- **Was → Now:** nothing produced the pages → a distillation pass over docs, README, agent instructions, key configs and synthesized per-module summaries seeded from the code index. Virtual module sources hash exactly like files, so an unmoved module short-circuits on the same ledger check as an unchanged file. Chunking is headings → paragraphs → hard slice with tail overlap, with headings inside code fences correctly not treated as headings.
- **Was → Now:** cost scaled with repo size on every pass → merge is cost-tiered: normalized containment unions provenance with zero model calls and a byte-identical body; a small page takes one rewrite call; a large page appends a delta fragment and preserves the old body verbatim. A dead source's fragments are cut with no call at all. The mock runner's call count is the token meter in tests — an unchanged repo is asserted to cost exactly zero calls.
- **Was → Now:** feeding file contents to a model is a prompt-injection surface → every byte read from disk is neutralized (reminder/rule/tool-call markers defanged, forged content markers rewritten) and quoted between explicit delimiters. The generated page type carries no path field at all, so a model-proposed path is structurally impossible to honor; paths are always derived canonically from type and title, which is also what makes re-distillation merge into the existing row instead of forking a duplicate. Resolved body paths are checked against the knowledge directory so a symlinked component cannot escape it.
- **Was → Now:** the lock bit was a convention → it is enforced at every write path independently. Distillation cannot overwrite a locked row, index entry or body file, cannot set the bit on a page the user did not lock, and the cascade spares locked pages; the tool's write path goes unlock → commit → re-lock and restores the prior lock state on every failure path; and sync transmits and honours the bit on arrival. Bodies are published only after their row write succeeds, so a locked page's file cannot be clobbered even within a single batch.
- **Was → Now:** retrieval injected full content and re-derived context per session → SessionStart emits one pointer line per page (id, type, title, snippet) capped at 600 tokens and clamped to the remaining hook budget, followed by an instruction to pull bodies through the tool. Ordering is (type, title, id) with nothing time-derived, so the injected prefix is byte-identical across runs and stays prompt-cache friendly.
- **Was → Now:** the weight table allocated 0.60 of every conceptual query to a semantic channel that had been removed and could only return an empty result — sixty percent of the weight mass evaporated, scaling every result down and distorting the relative order of the channels that did fire → channels now declare their capabilities, and a dead channel's mass is redistributed *proportionally* over the live ones, preserving the designed emphasis. Conceptual (0.20/0.60/0.20) becomes bm25 0.50 / temporal 0.50; a temporal query still favours temporal after the drop; the all-dead case falls back to bm25-only, which is safe because the searcher cannot be constructed without an index.
- **Was → Now:** pages were unreachable from search → an FTS channel over the page index with entity-graph link expansion (query candidates → seed entities → spreading activation → name lookup, capped at 5 seeds). Linked hits are clamped below the weakest direct hit, so a weak graph link can never outrank a literal match. Knowledge hits are unioned into the result set rather than applied as a multiplicative boost the way graph and code are — page ids never collide with entry ids, so a boost would have been a guaranteed no-op and pages could never have surfaced at all. The channel is off by default so entry-only callers do not start receiving a different doc type.
- **Was → Now:** no agent-facing surface → a `knowledge` meta-tool with search/read/write/list/status, plus `cas knowledge search` and `cas knowledge read` on the CLI. Manual writes default to a `manual://` provenance that never enters the source ledger and therefore can never be tombstoned.
- **Was → Now:** the codemap and project-overview skills were standalone generators → they query the store before regenerating and build after writing, making both docs views over it. Ported across harness flavors by prefix substitution with the drift guard green.
- **Was → Now:** the pull instruction shipped naming an action the router rejects, so a perfect-looking index invited body fetches that all returned an error — and the test asserting it could not fail, because it matched a word that also appears in the section header → the constant is corrected and pinned verbatim, and a new test parses the action out of the instruction and drives it through the real service router rather than the handler, closing the gap that let the text and the router drift (cas-core authors the instruction but cannot see the router). Verified by reintroducing the bad action and watching the test fail with the router's own error.
- **Was → Now:** cloud contributed nothing to knowledge → pages ride the existing sync push/pull incrementally, and an embedder produces vectors so semantic search is real (cloud query embedding → cosine kNN over a local cache). The capability gate is the constructor: logged out it is `None`, which means no HTTP and no vector-store environment created on disk at all. The cache is tagged with provider, model and dimensions so a model change wipes and re-arms it; zero vectors are refused at the boundary so a soft-failing provider leaves a page pending rather than poisoning ranking; and a process-wide registry stops the sync and search paths from double-opening the same environment. `has_semantic()` is now true only when a channel is attached *and* vectors are cached, so the capability-aware weights above never allocate mass to a channel that can only return nothing.
- **Coverage:** 25 cloud tests in both logged-out and mocked-cloud modes, 39 store tests, 45 pipeline unit + 11 mock-LLM integration tests, 14 retrieval/scorer tests, 7 tool-handler and 3 CLI tests.
