## Post 1 — User

Live on main — **User**

If you use Cassy on more than one project, your projects have been quietly reading each other's mail. This release finds that, stops the last two ways it happened, and makes the clean-up tool safe to actually run.

### Reply to Post 1

- **Was → Now:** two unrelated checkouts that happened to sit in folders with the same name shared one cloud bucket and merged each other's notes and tasks → the repository's own remote address decides the bucket, so same-named folders stay separate. An explicit pin still wins, and a project with no remote behaves exactly as before.
- **Was → Now:** nothing anywhere told you contamination had happened — the only symptom was another project's finished work showing up in your ready list, still looking open → the health check now reports it by default, read-only, and can list every affected row. It matches on id *and* title together, because short ids genuinely collide and matching on id alone would point you at deleting real work.
- **Was → Now:** two projects claiming the same bucket produced no warning at all → you get one naming both folders and the shared id. Second clones and worktrees of the *same* repository stay silent.
- **Was → Now:** starting a task that had been copied in from another project did so silently, and the work went to the wrong repository → you get a warning first, naming the project, the risk, and both ways out. It is advisory; the task still starts.
- **Was → Now:** the tool for purging those foreign rows previewed only a count, then deleted irreversibly → the preview lists exactly what will go. It now also refuses, and says why, when your last sync is missing or stale or you still have unsent local changes — the old behaviour on a long-idle machine deleted everything local and pulled a months-old snapshot over it. `--force` is the deliberate override, and the safety backup it takes beforehand is now actually complete.
- **Was → Now:** a message sent to an idle session could sit unseen for hours unless you interrupted it → ordinary messages wake it again. The worst case before this was two and a half hours with work already waiting.
- **Was → Now:** a green build badge implied the tests had run when that job only compiled them → the job is named for what it does, and the one job that runs the suite is marked. You will see the name change in your checks list: "Full Matrix" is now "Release-Profile & Build Guard (compile-only, no test suite)". A completely reproducible failure was hunted for a day as a "flaky test" because of this.

## Post 2 — Dev

Live on main — **Dev**

A sync leak fixed months ago left residual foreign rows on every multi-project machine, with no detection, an unsafe remediation path, and two live re-contamination routes. This closes all four.

### Reply to Post 2

- **Was → Now:** project id fell back to the parent folder name whenever nothing was pinned → the git `origin` remote is consulted first. Since that changes which bucket an unpinned repo with a remote resolves to, the health check reports the resolved bucket, the reason, and the exact command to pin the previous one.
- **Was → Now:** no detection existed for foreign rows → a read-only scan runs by default, with a full listing behind a flag. Keyed on `(id, trimmed title)`: 4-hex ids collide (73 pure collisions measured across 39 databases), so id-keyed deletion destroys real work — rows sharing an id but not a title get their own warning section for exactly that reason. Attribution uses local-activity tables that are never part of the sync payload, so the evidence is asymmetric: its presence proves a row is native, its absence proves nothing. A row is only called foreign when this database has no evidence and a peer does; otherwise it is reported unattributed, never accused.
- **Was → Now:** task start ran no nativity check when a task carried no work target, so replicated rows were leased, worked and closed from the wrong repo → a four-signal check (no work target, no dependency edge, no locally-registered assignee, sync configured) warns before leasing. Fail-silent and best-effort throughout: a failed lookup can never turn this into a failed start. The known false positive — an unassigned standalone task in a synced project — is pinned by a test whose comment records the decision, so it does not get "fixed" into a fifth veto.
- **Was → Now:** purge previewed a row count and copied a live WAL database as its backup → the dry run emits the concrete delete set (ids, titles, dependency-edge count, full set under `--json`); the backup uses `VACUUM INTO`, so it no longer omits every transaction still in the `-wal` sidecar; and the pending-pushes read fails closed — corruption, schema drift and undecodable rows previously all answered "nothing queued", disabling the unpushed-work refusal inside the destructive path.
- **Was → Now:** a successful merge moved only the local ref and returned a bare success string → the target branch is published and the outcome is stated on every receipt (pushed / already current / no remote / not pushed with reason). Bounded and non-fatal: an unreachable remote degrades to a loud not-pushed instead of hanging the handler or failing a completed merge. Non-force with a fully-qualified refspec, so a diverged remote is reported rather than clobbered.
- **Was → Now:** "the message left our outbox" was treated as proof of receipt, but the receiving layer files it away on a watcher whether or not anyone is looking → only evidence that the recipient actually surfaced the message consumes the row. The write-side storm protection that motivated the old shortcut is untouched.
- **Was → Now:** cleanup was gated out of the shared-checkout setup, so a checkout whose owner had finished without cleaning up had no supported removal path → cleanup is available there and can target one checkout by id, branch or owner. It refuses while the owner is live, and refuses to destroy uncommitted or unmerged work without an explicit force.
- **Was → Now:** a close rejection asserted the shared integration branch was unpublished purely from its name prefix → it resolves the remote ref and states whichever is true, so nobody chases a push that already happened.
- **Was → Now:** the uncommitted-work check returned an empty result for both "clean" and "could not inspect", and close treated both as a pass → those are now distinct. Close still refuses outright on uncommitted work; it additionally records an inspection that failed, leftover untracked files, or a checkout sitting on a commit other than the one being claimed. **This is detection, not a fix for any specific drift** — it makes an unverifiable close announce itself instead of looking identical to a verified one. The underlying report of an edit that was declined yet still landed on disk was not reproduced (28 attempts across two denial paths) and remains open; the interactive condition matching the original report could not be exercised and is untested.
- **Added:** a one-command clean-environment test run. Tests reading config from the environment passed locally and failed on fresh machines because the usual shells export a pile of variables — the variables are now enumerated from the live environment rather than a hardcoded list that had already drifted both ways, and the command prints what it stripped.
