## Thread 1 — User

**Top-level:**
Live on production — User: Cloud sync no longer gets stuck — it keeps itself moving and speaks up if something's wrong.

**Reply (Was → Now):**
Was: a busy machine could quietly sit on a backlog of unsynced changes for days before anyone noticed, and restoring something after a delete wasn't always safe. Now: pending changes drain automatically about once a minute even while you're actively working, you get a clear warning if a backlog starts piling up or going stale, and bringing something back after a delete is protected from being wiped out again by an old delete request. Moving your work to a second machine and picking up where you left off is dependable.

## Thread 2 — Dev

**Top-level:**
Live on production — Dev: Daemon cloud sync moved from idle-gated to true cadence-driven draining, with stricter delete/skip handling.

**Reply (Was → Now):**
Was: the background sync tick only fired once the daemon judged itself "idle," so a continuously active daemon could leave its local queue wedged indefinitely; delete pushes used a plural entity_type that the API rejected, deletes weren't marked failed on error, and an ambiguous cloud skip/count signal could get silently treated as success, dropping the retry. Now: the cloud-sync interval runs every tick regardless of activity, delete routes send the correct singular entity_type and mark_failed on error with a live-delete guard so a restored entity isn't removed by a stale tombstone, an unrecognized skip/count signal fails closed and keeps the row queued for retry instead of dropping it, and preflight surfaces configurable queue-depth and queue-age warnings before a backlog goes silent.
