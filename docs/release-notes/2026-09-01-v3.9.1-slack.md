## User thread

**Top-level:**
Live on production — **User** — Moving a task between projects now truly leaves the old project, the hub no longer dies with the worker that started it (nor takes your terminal with it when stopped), and release trains can keep workers from pushing by policy.

**Reply (Was → Now):**
- Was: a task moved to another project still left a copy behind under the old project until someone cleaned it up by hand. Now: the move removes the old copy and creates the new one in one step, and deleting a moved task removes it where it actually lives.
- Was: the hub started during an update from a factory worker quietly died when that worker was shut down, so Commander pairing failed with "hub is not running". Now: the hub runs on its own, outside the worker, and `cas hub` tells you who started it and if it exited.
- Was: stopping the hub could take down the terminal session that had started it, and everything running in that session. Now: stopping the hub only ever touches the process space Cassy created for it, and refuses anything else with a clear log line.
- Was: keeping workers from pushing branches during a release train relied on instructions in every task. Now: the train's delivery mode says so once, the close gate repeats it, and a push is refused.
- Install: use `cas update` for an existing installation, or download the
  v3.9.1 archive for Linux x86_64 (SHA-256 `{{LINUX_SHA256}}`) or macOS ARM64
  (SHA-256 `{{MACOS_SHA256}}`) from the GitHub release.

## Dev thread

**Top-level:**
Live on production — **Dev** — Move enqueues exactly delete(old key) + destination-keyed upsert; hub launcher escapes worker cgroup scope and `hub stop` only kills Cassy-owned scopes; `delivery_mode=local_merge` gate + guard.

**Reply (Was → Now):**
- Was: `SyncingTaskStore::update` on a move queued the generic team upsert (project_id NULL, pre-move payload) in addition to `queue_origin_project_move`'s rows, so the pusher key was re-created after the delete and deletes-after-move targeted the wrong key. Now: a move queues only delete(old)+upsert(dest), one push sends them delete-first, and later deletes target `task.origin_project`; verified live with a scratch task (old key empty, destination populated).
- Was: `cas hub` launched via setsid but inside the worker's cgroup; containment teardown killed it. Now: the launcher moves to the shared server scope before forking, `HubProcessRecord` carries sid/pgid/cgroup/launched_by, and status reports launcher + silent exits.
- Was: `HubProcessRecord.cgroup` recorded the hub's inherited `/proc/self/cgroup` for non-worker launches, so `hub stop` / stale replacement / failed-launch cleanup wrote `cgroup.kill` on the launcher's own terminal scope. Now: the record carries only the `cas-server-*` scope `join_shared_scope` created (null from a plain shell), and `kill_scope`/`remove_scope` refuse the caller's own scope, any ancestor, or any non-Cassy-named scope, with decision-table + detached lifecycle coverage.
- Was: no-push policy lived in task text and broadcasts. Now: `delivery_mode` on epics/sessions (inherited by children), MERGE REQUIRED text branches on it, worker skill documents both modes, PreToolUse guard rejects `git push origin` in local_merge (CAS_ALLOW_PUSH=1 override, logged).
- Validation and artifact: `cargo check --workspace --tests`, `cargo nextest run -p cas`, doctests, merge-queue validation of the single integration PR. The published archives are
  `cas-x86_64-unknown-linux-gnu.tar.gz` (SHA-256 `{{LINUX_SHA256}}`) and
  `cas-aarch64-apple-darwin.tar.gz` (SHA-256 `{{MACOS_SHA256}}`).
