## User thread

Top-level:

```text
*Live on production — User — Cassy v{{VERSION}}*
Was: each fix took its own trip through the merge queue. → Now: a whole release rides one train through it once.
```

Reply (Was → Now):

```text
*One trip through the queue per release*

• *Fixes ride the release train* — Was: each fix took its own merge-queue run, so a day of fixes meant a day of queue waits.
→ Now: new fixes collect on one release train, and the train goes through the queue once.

• *A bad fix comes off in one command* — Was: one broken fix in a release meant reworking the whole release.
→ Now: one command takes just that fix off, sends it back to be repaired, and the rest of the release carries on.

• *Releases land alone* — Was: a release could land together with another change, which forced a 20-minute rebuild of the downloads.
→ Now: the queue lands one change at a time while still testing five in parallel, so the prebuilt downloads are always used.

• *Failed changes go straight back for repair* — Was: when the queue rejected a change, someone had to send it back by hand.
→ Now: it returns to whoever built it, with the failing test named, automatically and once.

• *One review is enough* — Was: approved work was reviewed again whenever the branch underneath it moved.
→ Now: the approval carries over as long as the change itself is the same.

• *Far fewer GitHub calls* — Was: two machines ran into GitHub's rate limit three times in one night, and merges stalled.
→ Now: Cassy's background checks make about 93% fewer calls, and `cas doctor` shows who is spending them.

• *QA sticks to the code it checked* — Was: a QA pass could carry over to a later version with new code in it.
→ Now: it carries over only when nothing but generated files changed.

• *Pushes stop tripping on other people's changes* — Was: a check refused pushes over old lines the change never touched.
→ Now: it checks only the lines the change adds, against the branch it is going into.

Update with `cas update`, or choose <https://github.com/Richards-LLC/cassy/releases/tag/v{{VERSION}}|the Linux x86_64 or macOS ARM64 downloads>.
Linux x86_64 SHA-256: `{{LINUX_SHA256}}`
macOS ARM64 SHA-256: `{{MACOS_SHA256}}`
```

## Dev thread

Top-level:

```text
*Live on production — Dev — Cassy v{{VERSION}}*
Was: a queue run per fix, batched landings, 2,949 gh calls/h. → Now: one train run, singleton landings, 216/h.
```

Reply (Was → Now):

```text
• *Release train default* — Was: an epic-less task targeted trunk directly.
→ Now: it joins the open release-train epic cut from the integration branch; a landed train closes and the next opens on the next create. `target_branch` or `factory.release_train=false` opts out.

• *Train drop* — Was: no way to remove one child from a queued train.
→ Now: `cas factory train drop <task>... --reason` reverts named children with new revert commits, returns each to its worker and re-enqueues once; one repair cycle per train.

• *Cut notices* — Was: nothing said when a train was ready.
→ Now: one notice when reviewed fixes are merged with nothing in flight, and one at `factory.release_train_max_age_hours` (default 3); each names the project's own release command.

• *Singleton queue landings* — Was: max merge 5 let a release PR land in a group, so the landed tree id missed its prebuilt archives and release.yml rebuilt (+20 min on v4.0.5).
→ Now: release admission, doctor and the queue-health check require merge 1, ALLGREEN, build ≥5; repair commands preserve the rest of the ruleset.

• *Queue ejection repair* — Was: an ejected delivery PR waited for a manual request_changes.
→ Now: a failed run of the current tip reopens the task to its worker with job, step and failing tests; one cycle, then the operator is paged once. Hand repairs and a still-running entry ahead are not counted.

• *Review carry-over* — Was: target movement re-dispatched a verifier for an unchanged patch.
→ Now: an identical full-context patch-id carries the verdict with an audit note; verifier deadlines extend on live progress, up to one hour.

• *GitHub API budget* — Was: the CI watcher re-read merged PRs every 30 s and every caller retried into rate limits.
→ Now: merged PRs aren't polled, repo names cache for an hour, one merge-queue listing per repo per minute is shared across daemons, a rate-limit refusal pauses all callers for 2 min, and every call is logged per caller.

• *QA carry-over (#1552)* — Was: the carried-verdict patch comparison ignored whitespace and compared against a moving target.
→ Now: a descendant tip keeps the verdict only for `hub-web/dist`-only commits; a rewritten tip needs an identical whole-repo patch against its recorded target.

• *Fast rows* — Was: version-literals scanned whole changed files, and a first push compared against origin/main.
→ Now: only added lines are scanned, and a first push uses the task's target branch as its base.

• *Queued-main merges (#1549)* — Was: a failed queue or repository lookup fell back to a local merge into main.
→ Now: it refuses with "queue state unknown" and asks for a retry.

Validation: the merge queue checks the final release tree.

macOS ARM64 SHA-256: `{{MACOS_SHA256}}`
```
