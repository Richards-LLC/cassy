## What you can do now

### Reviews you can trust

#### Unclear reviews never count as approval

Was: A review record that was incomplete, or written by a newer Cassy, could be read as approved and let work close without a real review.

Now: Anything that is not clearly approved is treated as not approved, so work waits for a real review. Tested with the published programs: on a database 3.95.0 wrote, the published 3.94.0 kept two unreviewed tasks open and closed only the one that got a real approval.

#### Questions stay open

Was: When a reviewer needed a decision, it had to fail the review and start over.

Now: The reviewer asks, the answer goes on the same review, and nothing is redone.

#### Honest review counts

Was: Reviews that had only been requested showed up as errors, so the numbers looked far worse than they were: 39 of 42 "errors" in one 22-hour stretch.

Now: They show as waiting until a verdict arrives.

### Measuring what helps

#### First numbers on which features earn their place

Was: The ledger could hold feature ratings, but its report for v3.94.0 read "none recorded".

Now: This is the first report with them. Automatic memory cards, already removed in v3.94.0, were added 39,852 times and used 5. The context added when a session starts was added 5,761 times and opened 0 times; it still ships, and this release does not change it.


## Under the hood

### Verification

#### Fail-closed status

Was: 3.94.0 mapped unknown stored statuses to Approved (`from_str(...).unwrap_or_default()`, default Approved), and synced JSON with no status defaulted to Approved.

Now: Unknown and missing statuses parse as Error everywhere, so close refuses them.

#### Mixed-version safety

Was: New statuses would read as Approved on older binaries sharing a store during rollout. Against raw `pending` and `supervisor_call` rows, released 3.94.0 listed both as approved.

Now: `pending` and `supervisor_call` are stored as `error` plus a `status_detail` column that older binaries ignore. Published 3.94.0 (f862f92) read a store written by published 3.95.0 (4d893d0): all 4 rows list and show as error, the 2 unresolved tasks refuse close, and the approved control closes.

#### Supervisor-call verdict

Was: A reviewer question resolved its dispatch as error and forced a re-dispatch.

Now: `supervisor_call` keeps the dispatch open for one answer; final verdicts stay single-use.

#### Pending dispatches

Was: Dispatch-request placeholder rows were counted as error verdicts (39 of 42 "errors", 30 October 5:00 PM ET to 31 October 3:33 PM ET).

Now: They are `pending` and excluded from verdict and ledger counts. Ledger events already written stay as they are.

### Feature feedback

#### First measured verdicts in the ledger

Was: `cas ledger report --release v3.94.0` printed "none recorded" under Feature feedback.

Now: `cas ledger report --release v3.95.0` prints `ambient_recall` measured noise (39,852 injected, 1,095 opened, 5 used) and `session_context` measured noise (5,761 injected, 0 opened, 0 used). Noise means under 1% used across at least 20 injections. These are lifetime totals from the 8:22 PM ET backfill plus one 6-injection session, not this release's window.

### Removed

#### Last Jev residue

Was: A config shim still warned about and rewrote `[jev]` sections.

Now: Removed; old configs with `[jev]` still load silently. Its CHANGELOG entry is filed under 3.94.0, but the code left in 3.95.0.
