COMMANDER RELIABILITY · 05 OCT 2026 · INVESTIGATION cas-f01f

Keep the operator conversation available when its machine is offline

Commander already shares live replies and session history across authenticated viewers. Its message store and history path still depend on the target machine. Add an encrypted cloud inbox with a transactional local outbox, then make delivery receipts mean that a device actually stored the turn.

Decision and confidence

High confidence: the direct route has several independent failure boundaries; pairing success is not proof that authenticated browser traffic can reach the hub. The missing offline inbox is structural. High confidence: duplicate pairing and concurrent credential rotation are reproducible on an isolated installed hub. Inconclusive: the operator's exact Chrome profile permission and Prowl reboot/service configuration were not inspected. The reproduced LNA route matches the incident but does not prove that profile's permission setting.

Authentication and revocation

DPoP binds credential hash, public key, method, bare path, issued-at and unique proof ID. The hub permits ±60s skew, retains replay IDs for5min, issues90-day credentials with30-day idle limit and7-day absolute-expiry refresh grace. One fresh proof retry adopts hub time on retryable401; explicit expired credential attempts rotation once. Rotation overwrites the old hash and the browser writes its new catalog record; another tab has no adoption channel in main.ts. hub/auth.rs:27, :968, :1049, :1756; connection.ts:497, :934; main.ts:899.

WebSocket tickets are single-use, bound to exact origin/endpoint/device and expire after5min (auth.rs:1124). WS revalidation every250ms and revoke notification close active viewers (server.rs:2161, :2976). SSE authenticates once on open (server.rs:1830); its stream has no corresponding per-device revalidation branch. Catalog heartbeat will eventually reject revoked credentials and abort/reconnect, but an already-open SSE alone is not a continuous authorization check. Retained machine-event payloads therefore need a revocation audit in the diagnostics follow-up. Transport authentication does not make a display label a global operator account identity.

Delivery model: what exists now

An operator send follows browser → ticketed hub WS → validated daemon ClientMessage → project SQLite prompt_queue → supervisor injection. Its verified device provenance is stamped by the hub, not trusted from the JSON body (server.rs:2337, :2397; queue enqueue prompt_queue_store.rs:3383). Acknowledged means accepted by the machine queue; supervisor processing is later. Pending sends use bounded localStorage plus runtime ledgers and retain their client_ref through normal held-send replay. Unconfirmed sends deliberately are not blindly retried.

Replies are durable project queue rows with target=operator, factory_session and reply payload. The daemon reads up to10 pending replies, broadcasts, and waits for a hub receipt (queue_and_events.rs:4775). The hub sends to every authenticated session viewer (server.rs:2703), and only the intended device or wildcard can close its receipt; the receipt is sent after the hub sink write, not after browser storage. History SQL is session-scoped and shared, ignoring recipient filtering (prompt_queue_store.rs:5161; shared lane :578). Device ID remains provenance/receipt routing, not history privacy between this operator's devices. Authorization remains a session-view grant, not a global claim that every account can read every project.

The completed supervisor transcript mirror adds operator rows after a verified Commander interaction enables the lane (commander_mirror.rs:243/249), redacts/bounds text and dedupes by turn. Explicit target=operator remains the direct path; a supervisor final answer may mirror, but generic worker/tool chatter is not automatically an operator message. Without a verified lane, mirror exits. The operator's earlier “supervisor has to remember operator” observation therefore needs this qualification: the epic includes a limited automatic mirror, not unconditional all-agent forwarding.

Offline target machine: project rows remain on disk, but browser history currently requires a hub/daemon path. There is no durable cloud copy of this operator lane. Reaching another paired machine or the pairing relay does not reveal this machine's conversation. Attachments can have cloud artifacts, yet their history references/signed-view lookup still have their own grant/availability paths (server.rs:1919); encrypted inbox work must preserve attachment access while a hub is offline.

Machine events are a different store: hub-local events.json, bounded1024 entries, atomic persistence with best-effort warnings; SSE snapshots history before live delivery and skips broadcast lag. They are attention events, not the durable operator conversation. Recovery after corruption may reset sequence; a long-lived client that retained a greater last sequence could ignore new lower sequences until reload. This is source-inferred at events.rs:109/146 and connection.ts:1575, and belongs in gap/epoch diagnostics validation.

Proposed durable inbox and pairing boundary

Storage, ordering and delivery contract

Commit each operator-visible row and its operator_delivery_outbox entry in the same project SQLite transaction. A hub-level DB written after the project commit would introduce a crash gap. Immutable UUID event_id joins account/hub/project/session identity; project-local notification IDs alone collide across machines. Retry uploads until relay-storage ACK; never delete unsent outbox rows merely because one viewer saw a turn. Local availability stays usable when cloud fails.

Neon stores a new operator_events table, separate from ephemeral hub_pairing_requests, uniquely constrained on operator account +event_id, with account feed sequence, encrypted content/key_epoch and retention metadata. Relay-storage ACK commits the retained ciphertext. Per-device cursor/receipts prove replay/persistence; shared operator read watermark is a UX fact that must never suppress another device's replay. Use immutable feed sequence for delivery and causal/session metadata for display, not browser timestamps. Deduplicate by event_id and monotonic revision; edited/resolved notices are revisions, not new conversations. Gaps/expired retention produce an explicit history-unavailable interval.

Device online, tab open: subscribe and store before ACK, then render. Device offline/closed: retained replay on next account-authenticated connection. Hub offline after upload: already-relayed history stays readable. Hub offline before upload: local-only turns remain unavailable; state must say awaiting machine upload. New commands entered while hub is offline can be cloud queued only after explicit command authorization design, encrypted to the machine and marked pending-machine. A cloud receipt never means supervisor execution. Command execution needs stable command_id idempotence at the actual execution boundary; exactly-once arbitrary side effects cannot be promised merely by deduping queue inserts. First slice can ship read-only retained replies before offline-command intake.

Auth, encryption and one operator / many devices

One operator is an authenticated account principal. A machine's local operator_label is display text, not proof of account membership. Enroll each existing/new browser installation into that account's relay audience through explicit consent and proof of its key; maintain separate device_id, credential generation, origin and machine/session grants. Use scoped machine upload credentials and distinct relay device read credentials/DPoP audience. Never reuse/forward direct hub credentials at the cloud endpoint or broaden CORS.

Recommended content boundary: encrypt message bodies and attachments at producer to an operator feed key; wrap keys to enrolled installation keys, with versioned key epochs and authenticated event metadata. The relay sees account, machine, session, timing, size and cursors, but not body plaintext. Existing ECDSA P-256 signing keys are not automatically encryption keys; introduce reviewed key-agreement/encryption material and keep its roles separate. Hub still sees messages it originates/executes. Hosted JS compromise can read displayed/decrypted content, so E2EE does not cure a malicious static deploy. Explicitly document threat model, authenticated encryption, algorithm library and downgrade refusal before implementation.

New phone with all old devices offline cannot decrypt old history without recovery. Choose account recovery wrapping (opt-in recovery key/passphrase) or approval by an already-enrolled device; do not secretly escrow plaintext in cloud to make onboarding convenient. Until chosen, show enrollment/recovery needed. Revocation removes relay membership, closes new subscriptions and rotates future feed keys; it cannot erase previously downloaded plaintext. Retention/deletion must cover body ciphertext, key wraps, attachments and local caches, with audit metadata separately bounded. Direct-only deployments remain an explicit option.

Re-pairing proves possession of prior installation identity before rotating it; lost key means a new installation requiring explicit replacement/revoke choice. Same label/UA/email string is never a dedupe key. Coordinate refresh and catalog generations across tabs, then adopt newest credential before treating unknown_credential as terminal; measured E5 shows why this matters. Preserve staged/active/rollback semantics and explicit origin migration boundaries. Do not silently revoke Soundwave's14 legacy rows.

Observability: Reconnecting must name the evidence

Client transition record: event time, monotonic attempt/generation, machine/session pseudonym, build/protocol, layer, stage, reason_code, HTTP/refusal retryability, socket close code, request correlation ID, timeout, last successful heartbeat, next_retry_at and result of any bounded permission query. Use honest network_or_browser_policy_unknown for opaque fetch. “LNA denied” requires a denied permission/console diagnostic; health success cannot prove the authenticated origin is accepted.

Hub log/audit: publication vs local readiness, safe CORS/preflight counts, auth refusal code/server time, WS hello/version/generation, daemon attach/exit, queue-commit/relay-ACK/device-ACK and sequence-gap count. Existing request IDs/history-count logs are useful; no prompt, private key, credential, DPoP header, pairing URL/code or raw relay request body belongs in diagnostics. Correlate client silence with public health and server counters, rather than concluding silence means pairing is invalid.

Relay: upload/replay lag by account-authorized device, retained-sequence bounds, outbox backlog age, duplicate/rejected uploads, enrollment/revoke epoch and observed hub lease age. An independent watchdog must produce offline/recovery notices; a dead hub cannot announce its own death. Separate hub, Serve route and factory status. Machine telemetry is opt-in and data-minimized. Cloud's current successful pairing counts are insufficient delivery observability.

What remains uncertain and what would falsify this
