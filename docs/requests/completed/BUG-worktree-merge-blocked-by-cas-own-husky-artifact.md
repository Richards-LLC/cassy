# `worktree_merge` refuses on an untracked artifact that Cassy's own startup hook creates

Small, but it fired on every merge of the session and it trains supervisors into a dangerous habit.

## Symptoms

`coordination action=worktree_merge` aborts with:

```
MCP error -32603: Failed to merge worktree: Worktree has uncommitted changes
```

The "uncommitted changes" are `?? .husky/_/` — an untracked directory generated by the Cassy worker startup hook itself. No worker authored it, no worker can remove it without breaking their own hooks, and it appears in every worktree.

The only way through is `force: true`, whose documented meaning is "force operation even with uncommitted changes" — i.e. the supervisor must assert *there is no real uncommitted work* on every single merge, when the tool has given no way to distinguish Cassy's own residue from a worker's unsaved edits.

## Concrete evidence

Every `worktree_merge` this session required `force: true`: `factory/tender-hound-11` (twice), `factory/quick-puma-7` (twice), `factory/quick-sparrow-15` (twice), `factory/zealous-marten-56` (three times). In each case `git status --porcelain` in the worktree showed exactly one entry: `?? .husky/_/`.

Workers independently noticed and reported it as noise — three separate close messages contained variations of "the only remaining untracked path is pre-existing `.husky/_/`, unrelated to this task", spending worker tokens pre-emptively defending against a false positive.

## Why this matters more than it looks

`force: true` became reflexive. On this session's stalled-worker rescue, `quiet-spider-15` had **seven genuinely modified files** uncommitted alongside `.husky/_/`. A supervisor habituated to forcing past "uncommitted changes" would have merged straight over real, unsaved, unreviewed work. I only caught it because I inspected the worktree directly for unrelated reasons.

The guard is well-designed. Making it cry wolf on every merge is what defeats it.

## Likely root cause

The dirty check treats any non-empty `git status --porcelain` as blocking, without excluding paths that Cassy itself generates, and without distinguishing untracked (`??`) from modified (` M`).

## Proposed fix

- a) **Ignore Cassy-generated paths in the dirty check (leaned).** `.husky/_/` is created by the Cassy startup hook; the tool that creates it should not then refuse to merge because of it. A small exclusion list, or writing it to a gitignored path in the first place.
- b) Distinguish untracked from modified. Untracked files cannot be lost by a merge; modified tracked files can. Block on ` M`/` D`, warn on `??`.
- c) If it must still block, name the offending paths in the error. "Worktree has uncommitted changes" forces a manual `git status` every time; listing them would let the supervisor judge in one step — and would have made the seven-modified-file case impossible to miss.

## Resolution

**Resolved 2026-07-27 — shipped in cas v2.29.0 (`origin/main`).** Task: cas-006c

`.husky/_` (a Cassy-generated artifact) is excluded from the worktree dirty check, and the dirty check now names the offending paths instead of reporting a bare "uncommitted changes".
