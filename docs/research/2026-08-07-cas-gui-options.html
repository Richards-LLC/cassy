Decision document · 2026-08-07 · cas-src research

A graphical control plane for CAS sessions across machines

Operator goal, in the operator's words: “a graphical way to control CAS sessions on multiple systems without pissing off Codex/Claude sub usage.” Hard constraint: the GUI must observe and steer the existing subscription-authenticated CLI sessions — never re-implement agent calls over metered APIs, never multiply session count, never poll agents.

One-line verdict: build a thin per-machine “cas hub” (auth + one stable port over the daemon WebSocket and cas bridge that already exist) plus a small web client that vendors t3code's MIT-licensed ghostty-WASM terminal — Option B below. It adds zero model calls by construction, and roughly 80% of the server side is extension of code already in cas-src.

The options

A

Native remote control only (per-session phone steering)

Already in progress

Lean on each harness's own remote-steering (Claude Code's native remote control from the phone/claude.ai), with the CAS-side environment fix (tracked as cas-7d8e, per the coordinator — in progress) so factory worker sessions are eligible for it. Related groundwork already filed: per-worker CLAUDE_CONFIG_DIR control on spawn_workers (docs/requests/2026-08-04-per-worker-claude-config-dir.md).

What you get
Steer an individual worker's session from a phone through the provider's own app. Uses the exact session that already exists — no new processes, no new auth surface to build.
What has to be built
Essentially nothing new in this decision's scope: finish the env fix so spawned workers register for remote control. All provider-side.
Effort
S (finish work already underway)
Quota risk
None. Same session, same subscription; steering is not an extra model call beyond the turns you initiate anyway.
What it does NOT give you
No fleet view — no list of factories across machines, no pane grid, no worker/epic status, no supervisor visibility. Per-session and per-provider only: nothing equivalent is confirmed for Codex or Grok workers, so coverage is uneven across a mixed fleet. It answers “poke this one worker from my phone”, not “see and run my factories”.
B

Thin fleet dashboard: per-machine cas hub + new web client

Recommended

Adopt t3code's decentralized topology (no central control plane; client holds a machine list and fans out) on CAS's existing substrate. The factory daemon already serves a GUI-shaped WebSocket protocol — DaemonMessage::Output streams raw VT bytes per pane with scrollback, and ClientMessage::Input/Focus/Resize inject keystrokes[1] — but bound loopback-only on an ephemeral port with no auth[2]. cas bridge already provides token-authed HTTP + SSE: session events, pane tails, inbox, activity[3].

What you get
One browser UI (desktop and phone): machine list → factory list → live pane grid; read worker panes, send messages (same PTY-inject path the supervisor's deliver_to_worker uses), interrupt, watch worker/epic status from SQLite. Works uniformly for Claude, Codex, and Grok workers because it observes PTYs, not providers.
Reuse vs build
Reuse (fork, MIT): t3code's libghostty-WASM terminal component[4]; its pairing-token → short-lived WebSocket-ticket auth design[5]; its ~200-line tailscale serve manager pattern[6]. Extend (Rust, in cas-src): daemon WS + bridge into one authed stable port per machine that enumerates sessions and proxies pane streams. Build fresh: the web SPA itself (session list, pane grid, input/interrupt affordances).
Effort
M — hub is mostly extension of existing bridge/daemon code; the web client is the genuinely new piece.
Quota risk
Zero by construction. Attaches to PTYs the factory already runs, reads SQLite, injects keystrokes. Push-only (WS frames + SSE), no agent polling; N viewers of a pane share one PTY. Session count never changes.
What it does NOT give you
Not a chat-style rendered transcript per worker (v1 shows real terminal panes, which is what the TUI shows today); no offline/relay path for machines outside the tailnet unless added later; no mobile-native app (the web app on a phone is the v1 answer).
C

Fork t3code wholesale and adapt its server to drive CAS

Considered & rejected

t3code is MIT-licensed and explicitly fork-friendly[7], and its execution model is genuinely subscription-native: all five providers are spawned local CLIs on the user's existing login (Claude via Agent SDK pathToClaudeCodeExecutable[8], codex app-server[9], Cursor agent acp, grok agent stdio[10], OpenCode SDK), with zero metered inference anywhere in the server. So the fork is legal and the model is quota-safe — for t3code's own sessions.

What you get
A polished, shipped product surface immediately: web + Electron + mobile clients, remote access (bearer/Tailscale/relay/SSH), checkpoint diffs, approvals, terminals.
What has to be built
The hard, wrong part: t3code's server owns agent sessions through its provider drivers and assumes it is the sole execution boundary[11]. To “drive CAS” it would either (a) run its own Claude/Codex sessions alongside the CAS factory's — doubling live session count against the same subscriptions, the exact failure mode this project exists to avoid — or (b) require gutting its orchestration core to become a viewer of CAS PTYs, at which point you've rewritten it into Option B with a Node runtime dependency CAS doesn't have.
Effort
L — large adaptation of an alpha (v0.0.32, “very very early”[7]) Effect-TS event-sourced codebase, plus permanent divergence from upstream.
Quota risk
High in variant (a): parallel session ownership multiplies concurrent CLI sessions per account. Zero only after the rewrite that makes it Option B.
What it does NOT give you
Any awareness of CAS concepts — factories, epics, tasks, worktrees, the MCP tool surface, supervisor/worker roles — all of which would need bolting on.
D

No new UI: tailnet + existing surfaces (cas bridge + SSH attach)

Viable stopgap

Use what ships today, remotely: cas attach device:factory-id already resolves a device via the cloud API (GET /api/devices, Bearer) and execs ssh -t host -- cas attach <id>[12], giving the full factory TUI from any terminal on the tailnet. cas bridge exposes authed HTTP endpoints (pane tail snapshots, SSE session events, inbox, activity) that scripts or a phone SSH client can hit[3].

What you get
Cross-machine observation and control now, with zero new code: full TUI over SSH, pane text over HTTP, message delivery via existing paths.
What has to be built
Nothing (optionally: a static bearer token per bridge and SSH keys on the fleet, which is configuration, not code).
Effort
S (near-zero)
Quota risk
None. Same sessions, same paths as the local TUI.
What it does NOT give you
Anything graphical — it is exactly the terminal experience the operator asked to move beyond. One session per SSH window, no fleet overview, phone usability is poor (TUI in a mobile SSH client), and bridge auth is a static token with no pairing/revocation story.

Recommendation

Option B, with A continuing in parallel and D as the interim. B is the only path that delivers the actual ask — a graphical, multi-machine fleet view — while keeping the quota guarantee structural rather than behavioral: the GUI can only watch PTYs, read SQLite, and type. A is complementary (per-worker phone steering through the provider's own app) and already moving; it should not be blocked on B. C is rejected on the session-multiplication ground above; its value survives as vendored components and design patterns inside B. D costs nothing and covers the gap until B's first milestone.

First three build steps for B:

  1. 1 — cas hub MVP (Rust, cas-src). One stable, configurable port per machine. Extend cas bridge to enumerate factory sessions from session metadata + .cas/cas.db and to proxy WebSocket attaches to each daemon's existing loopback ws_port (daemons stay loopback-only). Port t3code's auth design: one-time pairing token (URL/QR) → stored session → short-lived WS ticket on upgrade, with revocation[5].
  2. 2 — Thin web client. Served statically by the hub. Browser-local machine list (t3-style, no central roster) → per-machine session list → pane grid. Render DaemonMessage::Output in a terminal surface — start with xterm.js for speed, evaluate swapping in the vendored ghostty-WASM component[4] (zig is already vendored in cas-src). Input box → ClientMessage::Input; status sidebar from bridge SSE + worker_status/epic_status reads.
  3. 3 — Tailnet exposure + first-class interrupt. Optional tailscale serve integration on the hub (port of t3code's manager[6]) so phones reach it over HTTPS MagicDNS; add a ClientMessage::Interrupt{pane_id} routed through the daemon's existing interrupt handling rather than raw byte injection.
