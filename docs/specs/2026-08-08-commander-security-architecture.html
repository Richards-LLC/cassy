Commander · H0 architecture decision

One browser origin. Direct hubs. Explicit authority.

The binding security architecture for Commander's browser catalog, machine-local hubs, proof-bound credentials, origin policy, session multiplexing, and controller arbitration.

The decision

Commander is a browser-only viewer and control surface over one per-machine CAS hub. It does not own agents, create model calls, or proxy a fleet through a central server.

Browser profile
Catalog + non-extractable device keys in controller-origin IndexedDB
→
Paired hubs
Exact Origin + DPoP + scope + audit; no central fleet proxy
→
Daemon sessions
Exactly one Commander-owned upstream WS per session; pane fan-out in hub

Each browser profile explicitly designates one paired hub as its controller origin. The app loads there and connects directly to every target hub. Each target records and authorizes that exact origin during pairing. Another origin starts with an empty catalog and requires re-pairing; catalogs and credentials are never silently copied, merged, or synchronized.

Zero added model callsViewing and reconnecting do not invoke a model or create another logical CAS session.
Machine-local trustIdentity, authorization, revocation, and audit remain under owner-only ~/.cas/hub/.
One writerMany devices may observe; one remote controller lease may mutate a session.

Consequence: if the controller hub is unavailable, that profile cannot load Commander, but daemons, CLI/TUI access, and running work continue. Moving origins deliberately costs a full re-pair because it changes the browser security domain.

Amendment · 2026-08-10 · optional hosted static controller origin

The controller-hub origin remains the default. An operator may choose the HTTPS hosted static controller origin https://hub.petrastella.io for a browser profile only as an explicit, per-machine trust grant; every target must be paired with cas hub pair --origin https://hub.petrastella.io. This supersedes the former outright rejection because t3code demonstrates the same static-SPA/direct-machine shape at app.t3.codes; it does not remove the hosted availability or supply-chain boundary.

Binding controls: static-only host (no APIs, redirects, server sessions, or credentials); immutable byte-identical hub-web/dist deployment named by cas-src commit, artifact digest, deploy owner, and rollback artifact; published Ghostty WASM hashes verified before deployment; no telemetry or credential egress to the host; and explicit device revocation/re-pairing for every origin move.

The deployment CSP forbids third-party runtime, inline/eval, forms, and framing. It may permit connect-src 'self' https: wss: because static CSP cannot enumerate the dynamic paired-machine catalog; Commander constructs authenticated fetches and WebSockets only from paired catalog entries, and hubs retain literal exact-Origin + DPoP + ticket checks. The hosted host is never a wildcard or proxy.

Commander fetches authenticated GET /v1/machine before enabling controls. Missing, unknown, newer, or incompatible schema/capabilities produce a visible banner and leave unsupported controls disabled. A compromised host/DNS/deploy authority can serve malicious same-origin JavaScript until detected; that accepted residual risk is revocable through rollback, device/origin revocation, and re-pairing.

Trust boundaries and state

Controller originTrusted application-code boundary. Same-origin XSS is a compromised paired device, handled by revocation and audit.
OS accountOther users are excluded by ownership and modes. Code already running as the CAS UID is an account compromise, not a boundary Commander claims to enforce.
Target hubIndependent enforcement point for exact Origin, identity, scope, tickets, leases, and durable attribution.

Normative topology

  1. At most one hub instance runs for a CAS account on a machine.
  2. The controller hub serves static assets; it does not proxy control, store the remote catalog, or cache remote sessions.
  3. Discovery may suggest endpoints but cannot grant trust, scopes, or catalog membership.
  4. Each hub opens exactly one Commander-owned daemon WebSocket per daemon/session, regardless of viewers, windows, or panes.
  5. Commander does not import the t3 agent-owning runtime or change model/session counts.

Hub-local files

~/.cas/hub/ is owner-only mode 0700. Identity keys, paired-device records, capability hashes, revocation state, and audit files are owner-only mode 0600. They never live in a project database or checkout. Creation/replacement is atomic and no-follow; wrong owner, type, symlink, or broad permissions fail closed.

Raw pairing codes, tickets, authorization headers, DPoP proofs, and private material never enter logs, URLs, crash reports, project databases, or analytics.

Browser identity and storage

The controller origin generates a non-extractable WebCrypto P-256 key. Pairing returns an opaque credential bound to its public-key thumbprint, a random device ID, device/operator labels, exact controller origin, explicit scopes, and lifecycle metadata.

Where it livesIndexedDB at the controller origin: key, opaque credential, labels, device metadata, and machine catalog.
Where it never livesNo cookies, Web Storage, URL, service-worker cache, export file, or browser sync for long-lived credentials.
LifetimeExpires after 90 days absolute or 30 days inactivity. Re-pairing is required; background renewal is forbidden.

Requests use Authorization: DPoP <opaque-credential> and a proof covering exact method, normalized URI, credential hash (ath), issued-at, and random jti. The hub permits at most 60 seconds of clock skew and caches used jti values for five minutes. Any mismatch, expiry, reuse, or revocation fails closed.

Origin, CORS, CSRF, CSP, and TLS

Exact browser origin

  • Every browser API and ticket request, and every WS upgrade, requires the paired origin's exact scheme, host, and effective port.
  • Missing, malformed, wildcard, reflected, suffix-matched, or null origins are rejected before session existence or auth details leak.
  • CORS echoes only the authorized origin, sets Vary: Origin, never uses wildcard origin, and never enables credentialed CORS.
  • Mutations are non-simple JSON methods. GET and HEAD are read-only. No cookies means exact Origin, DPoP, and WS tickets—not SameSite—are the CSRF controls.

No inline/eval/third-party runtime is allowed. Secure-scheme connect-src is not authorization: the client connects only to catalog entries and each target independently checks Origin, DPoP, and scope. Literal IPv6 loopback may be added only with equivalent browser-tested restriction. Plaintext hostnames, LAN targets, and wildcard subdomains are excluded.

Responses also send Referrer-Policy: no-referrer, X-Content-Type-Options: nosniff, framing-denial protections, and Strict-Transport-Security: max-age=31536000 on TLS origins. includeSubDomains is omitted because a hub must not assert policy for names it does not control.

Transport

Plaintext control is restricted to literal loopback. A non-loopback HTTP/WS listener must refuse startup. Remote control uses verified https/wss or a loopback hub behind a configured TLS-terminating loopback proxy such as tailscale serve. Direct hub termination requires TLS 1.3; the supported proxy must provide an equivalent browser-trusted policy. Forwarded identity is trusted only from that configured immediate peer; conflicting forwarding fails closed. Certificate, hostname, and UI bypasses are forbidden.

Pairing and WebSocket capabilities

Pairing challenge32 CSPRNG bytes, base64url; exact origin/hub/scope ceiling; 10-minute TTL; SHA-256 at rest; atomic one-time consume.
Abuse limitsFive attempts/source/minute, twenty/challenge/hour, invalidate after ten failures; generic errors and secret-free audit.
WS ticket32 CSPRNG bytes; five-minute TTL; hashed; exact device/origin/scope/session/endpoint binding; exactly one successful upgrade.

A pairing code may be entered manually or carried in a URL fragment, never a query string. The app removes a pairing fragment with history.replaceState before any request or navigation. Ticket-bearing query strings are redacted. Reconnection requires a fresh DPoP-authenticated ticket; credential expiry or revocation closes active downstream connections.

The default grant is read-only: machine:read, session:read, and pane:read. Every control or administrative scope requires explicit selection during pairing or later local re-authorization. Scopes are additive and do not imply one another. Targeted interrupt is additive and never silently becomes the legacy session-wide interrupt.

Attribution, pre-auth behavior, and control

Audit identity

Every accepted or denied mutation records UTC time, hub and request/event IDs, outcome, device/credential IDs, device and operator labels, controller origin, verified network identity where available, required scope, action, target IDs, and sanitized size/digest metadata. It never records raw input, prompt/output content, or credentials. Attribution follows semantic messages into the prompt queue; remote users never impersonate the supervisor.

Before authentication

A hub exposes only immutable app assets, protocol version plus boolean readiness, and exchange of a still-live challenge already bound to the exact caller origin. It exposes no host/user/path/label, session IDs or counts, pane/worker data, recent activity, device list, scopes, snapshots, scrollback, events, or mutation. Generic responses do not reveal whether a resource exists.

Controller lease

  • Any number of scoped devices may observe; exactly one remote device controls a session.
  • Lease acquisition is explicit compare-and-set; duration is 30 seconds and heartbeat is every 10 seconds.
  • Disconnect/reconnect does not preserve control. Release and transfer are explicit. Only hub:admin forces early takeover.
  • Every remote session mutation needs both its scope and the active lease. All lease transitions are audited and broadcast.
  • The local CLI/TUI is privileged and preempts remote control on its first detected mutation; H1 must make that event visible.

One upstream, safe fan-out

The hub keeps one canonical session cache and one upstream daemon WS per session. It adds session/pane identity downstream and filters pane subscriptions locally. Per-viewer queues are bounded: a slow viewer alone is disconnected or resynchronized and cannot block daemon reads, harm other viewers, or create another upstream.

Honest abrupt-death diagnostics

Upstream close is correlated with process/session state. Typed termination reports the best available exit code, signal, core-dump indication, last daemon event time, and next diagnostic step. Clean exit, SIGILL, other signals, lost transport, and unknown death remain distinct when evidence permits; unavailable fields say unknown. Diagnostics never call a model, start a replacement agent, or silently switch sessions.

Non-goals

  • No agent scheduling, prompt ownership, model calls, or replacement of factory coordination.
  • No hostile-process isolation within one Unix account.
  • No silent credential/catalog synchronization across profiles or origins.
  • No central fleet proxy or remote session-history store.
  • No removal of legacy interrupt; targeted interrupt is additive.
