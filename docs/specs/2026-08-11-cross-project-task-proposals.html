Design decision · 11 August 2026

Cross-project work should arrive as a proposal, not a foreign task replica.

Add a dedicated cloud proposal API and proposal store. Require an explicit target, gate the client to supervisors/directors, validate a shared-team grant in the cloud, stamp provenance there, and create an ordinary target task only after receiving-side acceptance.

Status: cloud + CLI implementedRemaining gate: cloud push-side provenance preservation confirmationAudience: CAS CLI + Cloud maintainersSource: cas-a0ba / cas#171Cloud: petra-stella-cloud#44

Decision context

Supervisors currently relay cross-project work through markdown. That loses priority, dependencies, status, deduplication, and machine-readable completion. The required experience is a tracked proposal that a target project can accept or reject, optionally blocking an origin task until the accepted target task closes.

This is creation only. Cross-project close, update, transfer, gate bypass, implicit target selection, and non-supervisor creation stay out of scope. The current generic sync path cannot preserve explicit targeting, granted authority, trustworthy provenance, and observable completion at the same time.

Why this one

The deciding criterion is whether the origin can learn that the target closed without weakening project-scoped pull. Only a cloud-owned dependency signal can do that. A dedicated API also stamps authenticated provenance and keeps proposed work outside the executable target backlog.

What we give up

Generic team push already carries task-shaped JSON and would be quicker. The selected design adds a migration and a cloud-first sequence. That delay is preferable to silently omitting automatic unblocking and presenting client-authored provenance as authoritative.

Reversal cost

The API is additive. Reversal disables proposal creation and archives the proposal/dependency tables; normal sync is untouched. Tasks already accepted are ordinary tasks and need no rollback migration.

Decided contract

Authorization predicate

Both gates must pass. CAS permits only a registered supervisor/director and refuses other roles before network I/O. Cloud requires bearer-token membership and two existing explicit projects in one shared team; it does not auto-register a target.

  1. Runtime refusal: Cross-project task creation requires a registered supervisor or director session.
  2. Grant refusal: Cross-project task creation requires membership in a team shared by the origin and target projects.

Team membership is the v1 grant. A future project allowlist may narrow it. Origin and target are explicit request fields and are never derived from cwd, a push envelope, or session defaults.

Proposed-state flow

  1. task create project=<target> takes an idempotency key; omitting project keeps today's local path.
  2. CLI checks role and active team, then sends the proposal without inserting a foreign local task.
  3. Cloud validates both projects, reserves a target task ID, stamps provenance, and stores proposed.
  4. An optional origin blocker is validated and recorded transactionally.
  5. Target supervisors list proposals separately; proposals are never ready, claimable, assignable, or ordinary open tasks.
  6. Accept atomically records accepted and materializes one normal target open task.
  7. Reject records actor, time, and reason; it creates no task and reports a failed handoff rather than silent unblocking.
  8. Target close resolves the external edge; origin returns to open only after all local and external blockers resolve.

Proposal states are proposed, accepted, and rejected. They are not TaskStatus values.

End-to-end planned flow

Wire and storage contract

POST /api/teams/{team_id}/task-proposals accepts explicit origin/target IDs, idempotency key, task payload, asserted CAS provenance, client identity, and an optional origin blocker. It returns 201 {proposal_id,target_task_id,state:"proposed",provenance}. Repeats return the same IDs. Expected errors: 403 missing shared-team grant, 404 unknown explicit project, 409 blocker absent from cloud state.

Triage uses a target-project proposal list and idempotent accept/reject endpoints. Opposite second decisions return 409. Dependency reconciliation is project-scoped and returns proposal state, target status, and resolution; rejection is handoff_rejected.

Cloud adds task_proposals: immutable task payload, state, explicit resolved project IDs, both provenance classes, decision audit, and unique (creator_user_id, client_request_id). It also adds cross_project_task_dependencies: explicit origin and target identities, blocks as the only v1 type, timestamps, and uniqueness against duplicate edges. CLI adds a local external-dependency projection, not a foreign task replica.

Scope truth

The local tasks table has no row-level project ID; its boundary is its owning .cas/cas.db. Pending proposals remain separate, so scope=project truthfully means the current CAS database and must name its canonical ID. scope=global is rejected; scope=all is documented as equivalent to the current project until a multi-project aggregator exists. The tool must not claim to filter a nonexistent column.

Current versus planned boundary

Implemented: create project=<target-canonical-id> selects the proposal path; proposal_inbox, proposal_accept, and proposal_reject keep triage separate; proposal_reconcile project=<current-canonical-id> projects dependency signals without foreign task replicas. The origin is accepted only from an explicit .cas/config.toml canonical ID, and registered supervisor/director authorization runs before cloud configuration or network setup. Project task listing names its current database boundary; all documents current-project equivalence; global is rejected.

Implementation acceptance tests

  1. Local create without project stays compatible.
  2. Worker/unknown roles fail before network I/O.
  3. No shared-team grant returns a named 403.
  4. No cwd inference; missing origin/target is an error.
  5. One idempotency key yields one proposal/task ID.
  6. Proposals stay outside ready/list until accepted.
  7. Accept creates one open task with visible provenance.
  8. Reject creates no task and audits reason.
  9. External blocker stays blocked while pending/open, flags rejection, and unblocks after close.
  10. Project task listing names its real database boundary.
