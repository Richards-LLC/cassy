External resource ownership for shared authenticated workers

Decision owner: Factory supervisor · Scope: CAS factory workers using a shared authenticated external MCP identity

Recommendation

Adopt supervisor-declared external-resource leases enforced by a policy-aware MCP gateway. Scope every lease to factory session, authenticated account, upstream server, resource type, and canonical resource ID. Begin with a Gmail thread adapter protecting draft create, update, and send; deny an unmapped bare draftId.

The failure class is supervisor-declared exclusivity with no enforcement point at the tool layer. Assignment prose bound neither the shared mailbox nor the connector call that could write or send a draft.

Decision context

The reported incident placed three drafts on Jess Webber’s thread, including two written by different workers three minutes apart. The connector reportedly accepts a bare draftId to send; a queued draft was reportedly sent during agent editing on 2026-08-12. It also reportedly returns draft bodies only to the writing session, so workers cannot reconcile each other’s work. Scoped peer-warning work is separately owned by cas-5068; it is advisory, not write enforcement.

This decision is needed before another multi-worker sweep uses a shared customer-facing identity. It adds CAS-local ownership policy in front of provider calls; it does not change provider authorization.

Why this one

The deciding criterion is whether the mechanism can reject an unsafe operation as it becomes side-effecting while preserving the shared mailbox. Only tool-adjacent enforcement meets that criterion without a new identity and sender model.

The lease must be supervisor-declared, not inferred from prose or a worker’s first write. The declaration makes customer scope explicit before work; atomic CAS storage makes it exclusive; the gateway makes it effective. A task lease is insufficient: one task may cover many customers and multiple tasks may touch one customer. For Gmail, key the lease by authenticated-account namespace plus normalized thread ID, bind successful draft creation to it, and reauthorize update/send against that binding.

Required design constraints

  1. Use registered CAS agent ID and factory session; never trust a caller-supplied worker name.
  2. Make uniqueness (factory_session, account_scope, upstream_server, resource_type, canonical_resource_id); task is attribution only, and no OAuth secrets are stored.
  3. Audit atomic claim, renew, release, transfer, expiry, death, and supervisor override; workers cannot release another worker’s live lease.
  4. Use tool-specific canonical-key adapters, not argument-name guessing.
  5. Deny protected writes when lease state/key/draft mapping is unknown or unreadable; preserve read-only calls where safe.
  6. Remove native direct-connector bypass, or implement the equivalent connector-side check.
  7. Audit actor, holder, operation, allow/deny, and lifecycle events without message bodies or credentials.

What we give up

Per-worker identities are stronger where provider support and a changed sender model are acceptable. The recommended gateway preserves a shared sender and cannot protect separate credentials that bypass it. That trade is intentional: make the current shared mailbox safe before multiplying accounts; retain per-worker identities for later tenant or sender separation.

Reversal cost

Protection is opt-in per server/tool, so disabling the Gmail policy restores current behavior without deleting the audit ledger. The expensive reversal is operational: removing it reintroduces the known double-draft/double-send hazard.

Follow-up tasks implied

  1. External-resource lease/history store, migration, expiry/recovery, and supervisor declaration/transfer/release APIs.
  2. Gateway caller context, protected-tool policy, and audited pre-dispatch allow/deny decision.
  3. Gmail thread/draft ownership adapter and shared-profile conflict/recovery regressions.
  4. No-bypass inventory and routing or connector-side enforcement across harnesses.
  5. Operator workflow, expiry/recovery documentation, and supervisor-visible audit tests.
  6. Coordinate cas-5068 peer warnings as a complement, never a substitute.

Open questions

  • Which Gmail tool schemas expose thread IDs on create/update/send, and can draft-to-thread lookup avoid exposing another worker’s body?
  • Can the factory hide or route native connector definitions consistently across Claude, Codex, and Grok?
  • What TTL and renewal UX fit long-running review without abandoned claims after worker death?
