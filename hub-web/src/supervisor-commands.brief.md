# Brief: supervisor commands

## Single idea

A command belongs to the selected supervisor, and its receipt says what that harness actually did.

## Hero form

An action ledger above the composer pairs each slash command with its effect; a header Commands button opens the same short list without taking another row on a phone.

## Emotional register

Quiet and deliberate: existing Glass surfaces, mono command names, plain consequence text, and explicit confirmation for clearing context, ending a session, or running Finish.

## Distinctive move

The command receipt separates submission from observed harness action, so a transport acknowledgement cannot masquerade as completion.

## Deliberately omitted

No terminal textbox, arbitrary arguments, or guessed support: the hub owns the allowlist, and the daemon chooses mappings from its supervisor's harness. A busy supervisor refuses a command rather than breaking its turn.

## Component and state ownership

The command palette owns filtering and keyboard selection. The existing conversation boundary supplies the selected machine/session and sends only structured controls through its lease. The hub checks scope, lease, allowlist and confirmation before forwarding. The daemon resolves the actual supervisor, checks readiness and owns command identity and execution evidence. Receipts remain tied to their conversation across selection changes.

A submission progresses through submitted, observed, refused or unconfirmed. Native model controls use a separate fixed allowlist while the model chooser is open. Output evidence names an opened chooser or displayed usage; only a native confirmation can claim a changed model. Exit and Finish use session-end evidence for completion.

## Design provenance

Uses hub-web/DESIGN.md, hub-web/src/tokens.css and hub-web/src/glass.css. Reuses the current header action, composer, dialog and receipt vocabulary in both schemes.
